# What exists

The modules built so far, one entry each: what it does, its switch and permissions, what it exports for other modules, and where its notes are. Moved out of the root `CLAUDE.md` (#370), whose Current Status says where the project stands. Read the entry of a module before using it from another one; read its own `CLAUDE.md` before changing it. Update this file when a module is finished.

Each module in this list, from Patients to the Import centre, keeps what was decided for it, and its own gaps, in `apps/web/src/features/<folder>/CLAUDE.md`, which Claude Code loads when a file of that folder is read. **Read it before changing the module in either app:** for work under `apps/api` it does not load by itself.

- **Web foundation:** session bootstrap, tenancy (picker, switcher, theming, formatters), access (`usePermission`, `<Can>`, `PermissionGuard`, policy refresh), the feature registry with slots, the app shell, i18n, error reporting, bundle budgets, the shared building blocks (data grid, charts, form kit, rich text), and the responsive target: every screen works at phone, tablet and desktop width, and Playwright runs every spec at all three (see Responsive Design).
- **Web auth:** login and sign-out, deep links (`/open/<kind>/<id>`), idle sign-out with a warning, cross-tab sync, the invite, forgot-password and reset-password pages, the authenticator code step at sign-in, enrolment at `/security`, and the account page at `/profile` (change password, end other sessions). Thirty-nine features are registered (the full list is `apps/web/src/registry/features.ts`; later ones are described below, and `platform` is not one of them). The first ones: `notices` (the sample feature and the template for new modules), `ui_examples` (the building-block examples), `patients`, `appointments`, `queue`, `triage`, `clinical`, `follow_ups`, `lab`, `radiology`, `pharmacy`, `inventory`, `indents`, `purchasing`, `departments`, `doctors`, `staff`, `services`, `drugs`, `lab_tests`, `wards`, `codes`, `templates` and `imports`.
- **Dashboard (web, #120):** the landing page at `/` renders the `dashboard.widgets` slot in a grid (one column on a phone, two on a tablet, three on a desktop), so each role sees the panels its permissions and the hospital's switches allow, and a role with none sees a notice saying so. The page names no feature. A panel that fails shows "This panel could not be shown" in its place (`Slot` gained `errorFallback`) and the others carry on. Panels today: latest notices (`notice:read`), people waiting in the OPD queue (`queue:read`), laboratory orders to collect and received (`labSample:read`) and stock alerts, low and expiring (`stock:read`). Each reads one row of its list for the total that comes with the first page, under a key of its own, and shows counts only, never a patient. `StatCard` and `Stat` (`shared/ui/stat-card`) frame a panel. Role-specific panels beyond these, and reports, are the rest of M12.
- **Patients (web and API):** the list with server-side search, registration with a duplicate check, the patient screen (it hosts the `patient.detail.tabs` and `patient.detail.actions` slots and exports `DetailTab`), editing with conflict detection, deep links, audit of every read and write, and the `patient.registered` and `patient.updated` events (#49 to #55). Behind the `patients` switch, with the field-level permission `patient.contact:read` for contact details. Exports `PatientSearch`, the box another screen chooses a patient with, and `usePatientName`, the name and MRN of a patient another screen was given the id of. An optional old registration number (#694) is kept, imported and found by exact search. Notes: `apps/web/src/features/patients/CLAUDE.md`.
- **Departments (web and API):** the list, adding, editing, archiving and restoring (#57, and the API in #61). Behind the `departments` switch and the `department:read` and `department:manage` permissions. Exports `useDepartmentOptions`. Notes: `apps/web/src/features/departments/CLAUDE.md`.
- **Doctors (web and API):** a profile for a staff member and regular weekly working hours (#58, and the API in #61). Behind the `doctors` switch and the `doctor:read` and `doctor:manage` permissions. A hospital with doctors on needs departments on. Leave and one-off changes to hours belong with appointments. The profile holds the registration number, its council and the qualifications a printed prescription names (#397), and says when one is missing. The API exports `credentialsOf` for the clinical module. Notes: `apps/web/src/features/doctors/CLAUDE.md`.
- **Staff (web and API):** the staff list, invitations (one person, or up to 200 from a CSV file), deactivating, reactivating and signing someone out everywhere, with the `staff:read`, `staff:invite` and `staff:manage` permissions (#59, and the API in #61). The web screen is behind the `staff` switch; the API is always on. Nobody acts on, or invites into, a role that holds more than their own. Changing a role belongs with role management. The invited view shows whether each invitation's email was sent, is being sent or could not be sent, and sends it again (#349). Notes: `apps/web/src/features/staff/CLAUDE.md`.
- **Hospital profile (web and API, #696):** `/hospital-profile`: the admin edits the address, phone, registration number and GSTIN that the letterhead prints (prescriptions, invoices and the rest), with `hospitalProfile:read` and `hospitalProfile:manage` (admin by default). `GET` and `PATCH /hospital-profile` with `expectedVersion` (409 `conflict`), tidied text, an empty value removes one, audited as `update` on `hospital_profile`. No module switch in the API; the screen is offered under the `staff` switch. Migration `0093` lets the app role update those columns of its own hospital. The session's tenant carries `gstin` and the letterhead prints it. Notes: `apps/api/src/features/hospital-profile/CLAUDE.md`.
- **Roles (API only, #137):** list, read, create, edit and delete roles, and the catalog of permissions, with `role:read` and `role:manage` (admin by default). Built-in roles keep their name and cannot be deleted; nobody grants beyond what they hold; the hospital always keeps someone who can manage roles and staff. The role list in the web app (#133): add, rename and delete custom roles, built-in ones protected; the permission matrix (#134): every permission by module with its scope, saved as a whole, unsafe toggles disabled and the server refusals (`last_admin`, `cannot_remove_own_access`) shown, a change made meanwhile by someone else merged before saving. Notes: `apps/api/src/features/roles/CLAUDE.md`, `apps/web/src/features/roles/CLAUDE.md`.
- **Services and prices (web and API):** the catalog of what the hospital charges for, with prices that have effective dates on one price list per hospital (#62, and the API in #298). Behind the `services` switch and the `service:read` and `service:manage` permissions. Desktop-only. Exports `useServiceOptions`, and `ServiceSearch`, the search box another module orders a service of one category with (#87). Notes: `apps/web/src/features/services/CLAUDE.md`.
- **Drugs and consumables (web and API):** the medicines and consumables the hospital keeps, with no price and no stock (#63, and the API in #299). Behind the `drugs` switch and the `drug:read` and `drug:manage` permissions. Desktop-only. Exports `DrugSearch`, the search box a clinical screen prescribes a medicine with (medicines only, not archived; it needs the `drugs` switch and `drug:read`, and works at every width), and `useMedicineName` (#81). Notes: `apps/web/src/features/drugs/CLAUDE.md`.
- **Lab tests (web and API):** the tests and panels the laboratory offers, with reference ranges by sex and age (#64, #286, and the API in #300). Behind the `lab_tests` switch and the `labTest:read` and `labTest:manage` permissions. Desktop-only. Linking a test to the service it is charged as also needs `service:read` and the `services` switch. Exports `LabTestSearch`, the search box a clinical screen orders a test or panel with (not archived; it needs the `lab_tests` switch and `labTest:read`, and works at every width, #82). The age rule is `features/lab-tests/age.ts`, which the mock shares and the API holds a copy of (a test fails when the two differ). Notes: `apps/web/src/features/lab-tests/CLAUDE.md`.
- **Wards, rooms and beds (web and API):** wards, their rooms and beds, and bed categories, each charged as a bed-day service of the price catalog (#65, and the API in #301). Behind the `wards` switch and the `ward:read` and `ward:manage` permissions. Desktop-only. Uses `useServiceOptions` and `useDepartmentOptions`. Occupied and being cleaned are set by admissions and housekeeping (R2), never from this screen. Notes: `apps/web/src/features/wards/CLAUDE.md`.
- **Policy capture and pre-authorization (web, mock only, #182):** an Insurance tab on the patient's screen (`patient.detail.tabs`, `policy:read`): policies against a payer's plan (add, end) and pre-authorization requests with the payer's answer (`preauth:read`, `preauth:manage`), and a cover panel on the new-invoice screen (new slot `invoice.builder.panels`) with the approved limit, what the visit has been billed and a warning from 80% of the limit. Endpoints are in the planned contract. Notes: `apps/web/src/features/insurance/CLAUDE.md`.
- **Insurers, TPAs and corporates (web, mock only, #181):** the organisations billed instead of the patient, their plans (patient share, limits, eligibility rules, covered or excluded services) and effective-dated rate agreements that never overlap, never start in the past and are only ended, never edited. Behind the `insurance` switch and the `payer:read` and `payer:manage` permissions. Desktop-only. Uses `ServiceSearch`, `toMinor` and `currencyDigits` from services. The API (#187: masters, policies, pre-authorizations, the coverage split and claims, corporate credit with receipts #803) is in `apps/api/src/features/insurance/CLAUDE.md`. Notes: `apps/web/src/features/insurance/CLAUDE.md`.
- **Operations (API only):** duty rosters, the blood bank, ambulances and bed cleaning tasks (#200). Four switches: `roster`, `bloodbank`, `ambulance`, `housekeeping`; permissions `roster:*`, `bloodUnit:*`, `ambulance:*`, `cleaningTask:*`. A blood unit moves through a state machine the API and the database both enforce, with its history kept append-only; a trip sends one ambulance at a time; a patient leaving a bed (`bed.released`) makes a cleaning task whose completion makes the bed available. The screens are housekeeping (#198), duty roster (#195), ambulances (#197) and the blood bank (#196), below. Notes: `apps/api/src/features/operations/CLAUDE.md`.
- **Admissions (API; web: the bed board, the admissions list and admitting):** admission, discharge and transfer (#156): an inpatient encounter opened with the admission, a bed given and changed with the history kept, discharge, the bed board with housekeeping and a server-sent stream. Behind the `admissions` switch (the beds need `wards` too) and the `admission:read`, `admission:create`, `admission:transfer`, `admission:discharge`, `admission:cancel` and `bed:update` permissions; an admission made by mistake is cancelled with a reason (#573, API only). The web app has the bed board (#151, `/beds`: beds by ward and status with who is in them, live over the event stream, mark cleaning or ready, block and unblock); admitting into a free bed and giving or changing a bed from the list (#152, `/admissions`); the inpatient census (#154, `/census`: occupancy by status and the admitted patients by ward and doctor; no expected discharges yet); advice, deposit and consents are not built. Web notes: `apps/web/src/features/admissions/CLAUDE.md`. Emits `admission.created`, `bed.assigned`, `bed.released`, `discharge.completed` and `admission.cancelled`. Notes: `apps/api/src/features/admissions/CLAUDE.md`.
- **Nursing and ward care (API only, #163):** for an admitted patient, ward vital signs kept apart from triage's, the medication administration chart (given, withheld, refused or missed against a medication order, each with a reason unless given), nursing progress notes with their history, the diet orders of the stay (read only) and requests to a store for ward stock (an indent linked to the stay). Behind the `nursing` switch (the stay needs `admissions`, the chart and diet `clinical`, stock requests `inventory`) and the `nursingVitals:read|record`, `mar:read|record` and `progressNote:read|write` permissions (nurse and admin record, doctor reads and writes progress notes). Append-only in the database: vitals, chart entries and note versions refuse UPDATE, DELETE and TRUNCATE to everyone. Emits `vitals.recorded`, `medication.administered`, `progressnote.created`, `progressnote.updated` and `ward.stockrequested`. Web: the worklist, vital signs and medication chart below (#157, #158); fluid intake and output with totals for a window, and care plans with tasks (#160, `fluidBalance:read|record`, `carePlan:read|write`; emits `fluid.recorded`, `careplan.created`, `careplan.task_done`, `careplan.closed`); ward stock requests have no screen yet; `GET /diet/kitchen-list` (#161) lists the admitted patients with the diet each is on (progress notes: see the web entry). Notes: `apps/api/src/features/nursing/CLAUDE.md`.
- **Running bill of an inpatient stay (web, mock only, #166):** `/billing/stays/:admissionId` from the admissions list: the stay's charge ledger by source with bed days to date, deposits, payments and balance, an estimate shown against the actual, and a link to the invoice builder for an interim bill. Final bill and settlement (#167): invoices against the ledger, a deposit set against an invoice or its excess paid back, and discharge gated by a per-hospital policy (`billing/discharge-policy`), all on planned endpoints (`/settlement`, `/deposits/apply`, `/deposits/refund`, `/billing/discharge-policy`). Planned endpoints (`/admissions/{id}/bill`, `/deposits`, `/bill-estimate`), so against the real API the screen shows an error until the API (#169). Notes: `apps/web/src/features/billing/CLAUDE.md`.
- **Discharge summary (web, mock only, #165):** `/admissions/:admissionId/summary` from the admissions list: six plain-text sections written as a draft (the course can start from a `discharge_summary` template), signed once by the doctor after a confirmation and then never changed, with addenda below it and a print view recorded in the audit log. `dischargeSummary:read`, `dischargeSummary:create`, `dischargeSummary:sign`. Planned endpoints (`/admissions/{id}/discharge-summary`, `/sign`, `/addenda`, `/print`), so against the real API the screen says it is not available until the API (#169). Notes: `apps/web/src/features/admissions/CLAUDE.md`.
- **Housekeeping (web, #198):** the bed cleaning task list at `/housekeeping` on the operations API: start, finish (makes the bed available) and cancel. Behind the `housekeeping` switch and `cleaningTask:read|work|manage`. Notes: `apps/web/src/features/housekeeping/CLAUDE.md`.
- **Nursing worklist and vitals charting (web, #157):** `/nursing` lists the admitted patients by ward and `/nursing/:admissionId/vitals` charts a stay's vital signs on the nursing API (#163): record, correct with a reason, a trend chart, an early warning score with configurable bands and abnormal readings and a rising score highlighted. Behind the `nursing` switch (also needs `admissions`) and `admission:read`, `nursingVitals:read|record`. The medication chart (#158) at `/nursing/:admissionId/mar` (`mar:read|record`): the doses due on a day from each order's frequency, charted given, withheld, refused or missed with dose checks and the patient's allergies, amended (never edited) with a reason. Doctor rounds (#159): `/nursing/rounds` lists the patients admitted under a doctor (`GET /admissions?doctorId=`, own doctor by default) and `/nursing/:admissionId/notes` has the progress notes of a stay, amended by their author with every version kept and shown in a history, and the stay's lab, imaging and procedure orders through clinical's `EncounterOrders` (`progressNote:read|write`; doctors now hold write). Fluid balance (#160) at `/nursing/:admissionId/fluids`: intake and output entries, corrected with a reason (the original stays), totals for the morning, evening and night shift and the day, worked out by the server; a shift column on the progress notes. Care plans (#160) at `/nursing/:admissionId/care-plan`: a problem, a goal and tasks, each marked done once, a plan ended as completed or cancelled. Diet orders and the kitchen list (#161) at `/nursing/kitchen` and `/nursing/:admissionId/diet` (`order:read`; a doctor places with `order:create`). Not built: assignment of patients to a nurse, ward stock screens, delivering the score settings with the tenant config. Notes: `apps/web/src/features/nursing/CLAUDE.md`.
- **Ambulances (web, #197):** trips and the fleet at `/ambulances` on the operations API: request a trip (patient optional), dispatch with an available ambulance, picked up, complete, cancel; add an ambulance and take it out of service or back. Behind the `ambulance` switch and `ambulance:read|dispatch|manage`. A trip can name a visit and a service, charged when it is completed (#589). The dispatch names a crew (driver, paramedic, attendant), shown on the trip (#590). Not built: changing the crew afterwards. Notes: `apps/web/src/features/ambulances/CLAUDE.md`.
- **Emergency (web, #171; API #175):** `/emergency` behind the `emergency` switch: quick registration (a complaint is enough; an unidentified patient gets a temporary ID), triage category 1 to 5 with waiting-time targets and an overdue mark, linking an unidentified patient to a record later, and the live board (polls every 10 s). Permissions `emergency:read`, `emergency:register`, `emergency:triage`. The API (BE-26, #175: `er_encounters`, temporary IDs, triage, linking to a patient and undoing the link within 24 hours, `er.*` events) is built; the screen has no undo yet. Care and disposition (ER-02, #172, against the real API): `/emergency/:caseId` with observation notes (also for an unidentified patient), starting treatment, rapid lab, imaging and procedure orders on an `er` encounter (clinical's order panels, so `order:create`), and the disposition (discharge, admit into an inpatient admission of type `emergency`, refer, expired), permissions `emergency:care` and `emergency:dispose`. Medico-legal cases (ER-03, #173): a case is flagged and its record (category, injury and history, police details) kept as revisions that are never overwritten, shown with a badge on the board; the details need `medicoLegal:read` and every view is audited, flagging needs `medicoLegal:manage`. Notes: `apps/web/src/features/emergency/CLAUDE.md`.
- **Operation theatre (API only, #180):** `theatre` module: theatres, surgery bookings that cannot overlap in a theatre, for a surgeon or for a patient (exclusion constraints), reschedule, cancel, start and complete, consumables that take stock out through the inventory ledger, `surgery.scheduled`/`started`/`completed`/`cancelled`. Permissions `theatre:read`, `theatre:manage`, `surgery:schedule`, `surgery:perform`. Notes: `apps/api/src/features/theatre/CLAUDE.md`. The web screen is the entry below (#176).
- **Operation theatre (web, #176):** `/theatre` on the theatre API: the day's surgeries (day picker, theatre filter), book with the patient, theatre, surgeon, time and an optional procedure service, reschedule, start, complete and cancel with a reason; add, rename and archive theatres. The server's `room_taken`, `surgeon_busy` and `patient_busy` refusals are said in words. Behind the `theatre` switch and `theatre:read|manage`, `surgery:schedule|perform`. Not built: a week or resource calendar view, consumables, the team (anaesthetists, nurses: no API), operation notes (OT-03, OT-04). Notes: `apps/web/src/features/theatre/CLAUDE.md`.
- **Operation theatre checklist and anaesthesia (#177, API #872):** a "Checklist and anaesthesia" row action opens fitness for surgery, the pre-operative and WHO safety checklist in four phases (each step timed and signed by whoever marks it, never undone) and the anaesthesia record (draft, then signed once). Served by the `theatre` API (migration 0114, event `surgery.checklist_step_completed`). Reuses `theatre:read` and `surgery:perform`.
- **Blood bank (web, #196, first slice):** blood units at `/blood-bank` on the operations API: stock by group and component, register a collected unit, test, clear, reserve for a patient, issue, transfuse, release, discard with a reason, expiry, and each unit's history. Behind the `bloodbank` switch and `bloodUnit:read|manage|issue`. Not built: donors, cross-match, transfusion reactions and the donor-to-recipient trace (the API has none yet). Notes: `apps/web/src/features/blood-bank/CLAUDE.md`.
- **Diagnosis and procedure codes (web and API):** the ICD-10 and procedure code sets, searched on the server, and each hospital's favourites (#66, and the API in #302). A set is loaded by an operator from a file (`pnpm --filter api codes:load`); none is in the repository, and which edition the pilot loads is #304. Behind the `codes` switch and the `code:read` and `code:manage` permissions. Exports `CodeSearch`, the search box a clinical screen records a diagnosis or a procedure with; a screen that uses it needs the `codes` switch and `code:read`. The management screen is desktop-only; the search box is not. Notes: `apps/web/src/features/codes/CLAUDE.md`.
- **Document templates (web and API):** each hospital's own texts for a prescription, a clinical note, a consent form, a discharge summary and an imaging report (#97), with placeholders and append-only versions (#67, and the API in #303). The one change ever made to a saved version is a redaction: the name and the text of an older version are removed, with a reason from a list (#292). Behind the `templates` switch and the `template:read`, `template:manage` and `template:redact` permissions. Desktop-only. Exports `fillPlaceholders` and `placeholdersIn`, which the clinical modules fill a template and check the result with, and `useTemplateChoices`, the templates of one kind in use and a way to read one's text (radiology's report, #97). The shared rich text editor gained `insertable`, a list of fixed texts to put in at the cursor. Notes: `apps/web/src/features/templates/CLAUDE.md`.
- **Import centre (web and API):** services and prices, drugs, single lab tests and patients loaded from a CSV file: the columns matched in the browser, every row checked by a job before anything is written (the dry run, with a report by line and field), and the batch written by another job in one transaction, whole or not at all (#68). Behind the `imports` switch and the `import:read` and `import:run` permissions; loading a kind also needs that kind's own permission, and patients need `patient:import`. Desktop-only. A feature makes its records importable by registering a kind (`app.importKinds`) whose `prepare` and `write` its create route uses too. Notes: `apps/web/src/features/imports/CLAUDE.md`.
- **Appointments (web and API):** the list of a range of days at the hospital, filtered by doctor and by status, a page at a time, opening on the signed-in doctor's own schedule (#70), one doctor's day or week as a calendar, the week at desktop width only (#72), and booking: a patient, a doctor and one of the doctor's free times worked out by the server, with an idempotency key, and the next free times offered when someone else took the time first (#71), and the appointment's own screen, where it is moved, cancelled with a reason, completed or marked a no-show, shown at once and put back if refused (#73). Behind the `appointments` switch, `appointment:read`, `appointment:create` and `appointment:update`. Works at every width. Hosts `appointment.row.badges` and `appointment.form.fields`. The API (#75) decides double booking with exclusion constraints on the doctor and the patient, and `db:seed` books sample appointments around today. Notes: `apps/web/src/features/appointments/CLAUDE.md`.
- **OPD queue (web and API):** today's tokens per department and doctor: a token issued at the desk to a walk-in, with the department's next number from the server, an optional doctor of that department and a priority (#76), and the board, in three groups (now serving, waiting, skipped) in call order, where a doctor's queue is called next, called again, skipped, put back and given a priority. The board follows the hospital's server-sent events (`GET /queue/events`, which say which department changed, never who) and reads the queue again on each; while the stream is down it reads every 15 seconds. Behind the `queue` switch, `queue:read`, `queue:create`, `queue:call` and `queue:cancel` (cancel a token issued by mistake or for a patient who left, #377). The waiting-room display (#78) at `queue/display`, opened from the board: token numbers and the doctor they go to from `GET /queue/display`, no patient. Works at every width. Adds "Issue a queue token" to the patient's screen through `patient.detail.actions`, and "Check in" to today's scheduled appointments, in the list and on the appointment's screen (`appointment.row.actions`, `appointment.detail.actions`, #376): a token for the appointment's doctor, ordered at the booked time when the patient came before it. The core gained `followEventStream` (`shared/api/events.ts`), which reads any event stream through the API client. The API (#79) numbers the tokens from a locked counter per department and day, serialises a doctor's calls, and passes changes to the boards through Postgres `LISTEN`/`NOTIFY` (`core/live`); `db:seed` adds five tokens of today in General Medicine at each sample hospital. Notes: `apps/web/src/features/queue/CLAUDE.md`, and for the API `apps/api/src/features/queue/CLAUDE.md`.
- **Triage (web and API):** vitals (blood pressure, pulse, temperature, SpO₂, weight, height), the chief complaint and the allergies of a patient (#77), recorded from a token of the queue board (`triage/:patientId?token=<id>`, through the new `queue.row.actions` slot) or the patient's "Vitals and allergies" tab (`patient.detail.tabs`), with values outside the hospital's ranges marked as typed. Readings are append-only (a correction names the reading it corrects) and carry the queue token until the encounter exists (M7). The ranges come from the server per patient, by age band (infant, child, adolescent, adult; #379), and a hospital admin edits them on a desktop screen (`triage/ranges`, `vitals:configure`, #378): a change applies from then on, and a reading keeps the marks (`flags`) it was recorded with. Behind the `triage` switch, `vitals:read`, `vitals:record`, `vitals:configure`, `allergy:read` and `allergy:update`. Works at every width. Allergies may name a catalog entry or a medicine (#380): the substance field searches a shared allergen catalog (drug classes, foods, others) and the hospital's own medicines on the server, and a coded allergy carries what it covers, so prescribing and the pharmacy warn by drug class (a penicillin allergy warns for amoxicillin); free text is still kept, matched by words. Exports `TriageSummary` (allergies and the newest reading) for the consultation view (#80), and `useAllergies` for the checks of prescribing (#81). The API (#79) keeps readings append-only in the database too, uses built-in ranges for each band a hospital has set none for (`db:seed` gives the clinic its own), and attaches a token's readings to the encounter `encounter.opened` names. Notes: `apps/web/src/features/triage/CLAUDE.md`, and for the API `apps/api/src/features/triage/CLAUDE.md`.
- **OPD consultation (web, #80; API #86):** "Start consultation" on the token being served (`queue.row.actions`) and on today's appointment (`appointment.row.actions`, `appointment.detail.actions`, now given `patientId`), the consultation at `encounters/:encounterId` with `TriageSummary`, notes kept as drafts on the server as they are written then signed or amended, diagnoses (ICD-10 through `CodeSearch`, words, or both; retracted with a reason), prescriptions (#81: medicines from the catalog through `DrugSearch`, with dose, route, frequency, days, quantity and instructions, warnings of a listed allergy and of a medicine already prescribed, and revising), printing a prescription and the visit summary under the hospital's letterhead (address, phone and registration number from the tenant config), with the prescriber's qualifications and registration number and a signature line, saying on the page what is missing (#397), each print recorded in the audit log first (#89), lab orders (#82: tests and panels from the catalog through `LabTestSearch`, with a priority and instructions, their status in words, a warning of one already in effect, and cancelling with a reason; their released results in the laboratory's `LabResultsPanel`, #92), imaging and procedure orders (#87: services of that category through `ServiceSearch`, otherwise as lab orders; no reports yet), closing and cancelling, the consultations list at `encounters`, and a "Clinical timeline" tab on the patient's screen (#83: the patient's visits newest first, a page at a time, filtered by type of visit and status; `GET /encounters` gained `type`). Behind the `clinical` switch, `encounter:read`, `encounter:create`, `encounter:update`, `clinicalNote:read`, `clinicalNote:write`, `diagnosis:read`, `diagnosis:write`, `prescription:read`, `prescription:create`, `encounter:print`, `order:read`, `order:create` and `order:cancel`; notes, diagnoses, prescriptions and orders are each hidden without their permission. ## Known gaps

- **The authenticator (two-step sign-in) is off for every hospital unless it is switched on.** Two per-hospital switches in `tenant_features` control it: `mfa` offers it to the staff (the set-up screen at `/security` and the link on the account page), and `mfa_required` with it makes it compulsory, which the server enforces (403 `mfa_required` on every route of the hospital until one is set up). There is no screen for the switches yet: they are set in the database or the seed until the platform admin module exists. There is no per-role requirement; that belongs with the roles API (#137).
- The account page (`/profile`) works against the real API (#257, `core/auth/account-sessions.ts`): changing the password (with an authenticator code for someone who has one) and ending other sessions. Not built: the account page's disabling of the authenticator (#252) and a screen for the account events written to `account_events`.
- Disabling the authenticator and regenerating recovery codes have no screen yet (#252), and `/security` is reached from the account page only when no authenticator is set up.
- Not checked yet, although stated as targets in Responsive Design: a phone Lighthouse run (the Lighthouse CI job, #457, audits the desktop preset and one Slow 4G run). Known from it: the appointment list misses LCP (about 2.7 s) and CLS (about 0.26) and only warns.
- The dev seed runs only against a database on this machine; another host has to be named with `--allow-host` (see `apps/api/CLAUDE.md`).
- `pnpm audit` reports two moderate advisories in `react-router` 6, fixed only in 7.x. CI gates at high.
- Production needs `MFA_ENCRYPTION_KEY` and `REPORT_URL_SECRET` (`openssl rand -base64 32` for each), and the migrate step needs the same environment as the API (it also applies default role permissions).
- **R2 hardening (#170):** review and runbook in `docs/R2-HARDENING.md`; the load test waits for staging.
- **Discharge and inpatient billing (API, #169):** discharge plan and clearances, the discharge summary (signed once, addenda), running bill, deposits, settlement and discharge policy, and an hourly job posting bed-day charges once per admission and date. Notes: `apps/api/src/features/admissions/CLAUDE.md`, `apps/api/src/features/billing/CLAUDE.md`.
