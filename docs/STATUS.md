# What exists

The modules built so far, one entry each: what it does, its switch and permissions, what it exports for other modules, and where its notes are. Moved out of the root `CLAUDE.md` (#370), whose Current Status says where the project stands. Read the entry of a module before using it from another one; read its own `CLAUDE.md` before changing it. Update this file when a module is finished.

Each module in this list, from Patients to the Import centre, keeps what was decided for it, and its own gaps, in `apps/web/src/features/<folder>/CLAUDE.md`, which Claude Code loads when a file of that folder is read. **Read it before changing the module in either app:** for work under `apps/api` it does not load by itself.

- **Web foundation:** session bootstrap, tenancy (picker, switcher, theming, formatters), access (`usePermission`, `<Can>`, `PermissionGuard`, policy refresh), the feature registry with slots, the app shell, i18n, error reporting, bundle budgets, the shared building blocks (data grid, charts, form kit, rich text), and the responsive target: every screen works at phone, tablet and desktop width, and Playwright runs every spec at all three (see Responsive Design).
- **Web auth:** login and sign-out, deep links (`/open/<kind>/<id>`), idle sign-out with a warning, cross-tab sync, the invite, forgot-password and reset-password pages, the authenticator code step at sign-in, enrolment at `/security`, and the account page at `/profile` (change password, end other sessions). Nineteen features are registered: `notices` (the sample feature and the template for new modules), `ui_examples` (the building-block examples), `patients`, `appointments`, `queue`, `triage`, `clinical`, `follow_ups`, `lab`, `departments`, `doctors`, `staff`, `services`, `drugs`, `lab_tests`, `wards`, `codes`, `templates` and `imports`.
- **Patients (web and API):** the list with server-side search, registration with a duplicate check, the patient screen (it hosts the `patient.detail.tabs` and `patient.detail.actions` slots and exports `DetailTab`), editing with conflict detection, deep links, audit of every read and write, and the `patient.registered` and `patient.updated` events (#49 to #55). Behind the `patients` switch, with the field-level permission `patient.contact:read` for contact details. Exports `PatientSearch`, the box another screen chooses a patient with, and `usePatientName`, the name and MRN of a patient another screen was given the id of. Notes: `apps/web/src/features/patients/CLAUDE.md`.
- **Departments (web and API):** the list, adding, editing, archiving and restoring (#57, and the API in #61). Behind the `departments` switch and the `department:read` and `department:manage` permissions. Exports `useDepartmentOptions`. Notes: `apps/web/src/features/departments/CLAUDE.md`.
- **Doctors (web and API):** a profile for a staff member and regular weekly working hours (#58, and the API in #61). Behind the `doctors` switch and the `doctor:read` and `doctor:manage` permissions. A hospital with doctors on needs departments on. Leave and one-off changes to hours belong with appointments. The profile holds the registration number, its council and the qualifications a printed prescription names (#397), and says when one is missing. The API exports `credentialsOf` for the clinical module. Notes: `apps/web/src/features/doctors/CLAUDE.md`.
- **Staff (web and API):** the staff list, invitations (one person, or up to 200 from a CSV file), deactivating, reactivating and signing someone out everywhere, with the `staff:read`, `staff:invite` and `staff:manage` permissions (#59, and the API in #61). The web screen is behind the `staff` switch; the API is always on. Nobody acts on, or invites into, a role that holds more than their own. Changing a role belongs with role management. Notes: `apps/web/src/features/staff/CLAUDE.md`.
- **Services and prices (web and API):** the catalog of what the hospital charges for, with prices that have effective dates on one price list per hospital (#62, and the API in #298). Behind the `services` switch and the `service:read` and `service:manage` permissions. Desktop-only. Exports `useServiceOptions`, and `ServiceSearch`, the search box another module orders a service of one category with (#87). Notes: `apps/web/src/features/services/CLAUDE.md`.
- **Drugs and consumables (web and API):** the medicines and consumables the hospital keeps, with no price and no stock (#63, and the API in #299). Behind the `drugs` switch and the `drug:read` and `drug:manage` permissions. Desktop-only. Exports `DrugSearch`, the search box a clinical screen prescribes a medicine with (medicines only, not archived; it needs the `drugs` switch and `drug:read`, and works at every width), and `useMedicineName` (#81). Notes: `apps/web/src/features/drugs/CLAUDE.md`.
- **Lab tests (web and API):** the tests and panels the laboratory offers, with reference ranges by sex and age (#64, #286, and the API in #300). Behind the `lab_tests` switch and the `labTest:read` and `labTest:manage` permissions. Desktop-only. Linking a test to the service it is charged as also needs `service:read` and the `services` switch. Exports `LabTestSearch`, the search box a clinical screen orders a test or panel with (not archived; it needs the `lab_tests` switch and `labTest:read`, and works at every width, #82). The age rule is `features/lab-tests/age.ts`, which the mock shares and the API holds a copy of (a test fails when the two differ). Notes: `apps/web/src/features/lab-tests/CLAUDE.md`.
- **Wards, rooms and beds (web and API):** wards, their rooms and beds, and bed categories, each charged as a bed-day service of the price catalog (#65, and the API in #301). Behind the `wards` switch and the `ward:read` and `ward:manage` permissions. Desktop-only. Uses `useServiceOptions` and `useDepartmentOptions`. Occupied and being cleaned are set by admissions and housekeeping (R2), never from this screen. Notes: `apps/web/src/features/wards/CLAUDE.md`.
- **Diagnosis and procedure codes (web and API):** the ICD-10 and procedure code sets, searched on the server, and each hospital's favourites (#66, and the API in #302). A set is loaded by an operator from a file (`pnpm --filter api codes:load`); none is in the repository, and which edition the pilot loads is #304. Behind the `codes` switch and the `code:read` and `code:manage` permissions. Exports `CodeSearch`, the search box a clinical screen records a diagnosis or a procedure with; a screen that uses it needs the `codes` switch and `code:read`. The management screen is desktop-only; the search box is not. Notes: `apps/web/src/features/codes/CLAUDE.md`.
- **Document templates (web and API):** each hospital's own texts for a prescription, a clinical note, a consent form and a discharge summary, with placeholders and append-only versions (#67, and the API in #303). The one change ever made to a saved version is a redaction: the name and the text of an older version are removed, with a reason from a list (#292). Behind the `templates` switch and the `template:read`, `template:manage` and `template:redact` permissions. Desktop-only. Exports `fillPlaceholders` and `placeholdersIn`, which the clinical modules fill a template and check the result with. The shared rich text editor gained `insertable`, a list of fixed texts to put in at the cursor. Notes: `apps/web/src/features/templates/CLAUDE.md`.
- **Import centre (web and API):** services and prices, drugs, single lab tests and patients loaded from a CSV file: the columns matched in the browser, every row checked by a job before anything is written (the dry run, with a report by line and field), and the batch written by another job in one transaction, whole or not at all (#68). Behind the `imports` switch and the `import:read` and `import:run` permissions; loading a kind also needs that kind's own permission, and patients need `patient:import`. Desktop-only. A feature makes its records importable by registering a kind (`app.importKinds`) whose `prepare` and `write` its create route uses too. Notes: `apps/web/src/features/imports/CLAUDE.md`.
- **Appointments (web and API):** the list of a range of days at the hospital, filtered by doctor and by status, a page at a time, opening on the signed-in doctor's own schedule (#70), one doctor's day or week as a calendar, the week at desktop width only (#72), and booking: a patient, a doctor and one of the doctor's free times worked out by the server, with an idempotency key, and the next free times offered when someone else took the time first (#71), and the appointment's own screen, where it is moved, cancelled with a reason, completed or marked a no-show, shown at once and put back if refused (#73). Behind the `appointments` switch, `appointment:read`, `appointment:create` and `appointment:update`. Works at every width. Hosts `appointment.row.badges` and `appointment.form.fields`. The API (#75) decides double booking with exclusion constraints on the doctor and the patient, and `db:seed` books sample appointments around today. Notes: `apps/web/src/features/appointments/CLAUDE.md`.
- **OPD queue (web and API):** today's tokens per department and doctor: a token issued at the desk to a walk-in, with the department's next number from the server, an optional doctor of that department and a priority (#76), and the board, in three groups (now serving, waiting, skipped) in call order, where a doctor's queue is called next, called again, skipped, put back and given a priority. The board follows the hospital's server-sent events (`GET /queue/events`, which say which department changed, never who) and reads the queue again on each; while the stream is down it reads every 15 seconds. Behind the `queue` switch, `queue:read`, `queue:create` and `queue:call`. Works at every width. Adds "Issue a queue token" to the patient's screen through `patient.detail.actions`, and "Check in" to today's scheduled appointments, in the list and on the appointment's screen (`appointment.row.actions`, `appointment.detail.actions`, #376): a token for the appointment's doctor, ordered at the booked time when the patient came before it. The core gained `followEventStream` (`shared/api/events.ts`), which reads any event stream through the API client. The API (#79) numbers the tokens from a locked counter per department and day, serialises a doctor's calls, and passes changes to the boards through Postgres `LISTEN`/`NOTIFY` (`core/live`); `db:seed` adds five tokens of today in General Medicine at each sample hospital. Notes: `apps/web/src/features/queue/CLAUDE.md`, and for the API `apps/api/src/features/queue/CLAUDE.md`.
- **Triage (web and API):** vitals (blood pressure, pulse, temperature, SpO₂, weight, height), the chief complaint and the allergies of a patient (#77), recorded from a token of the queue board (`triage/:patientId?token=<id>`, through the new `queue.row.actions` slot) or the patient's "Vitals and allergies" tab (`patient.detail.tabs`), with values outside the hospital's ranges marked as typed. Readings are append-only (a correction names the reading it corrects) and carry the queue token until the encounter exists (M7). The ranges come from the server per patient, adults only (#378, #379). Behind the `triage` switch, `vitals:read`, `vitals:record`, `allergy:read` and `allergy:update`. Works at every width. Exports `TriageSummary` (allergies and the newest reading) for the consultation view (#80), and `useAllergies` for the checks of prescribing (#81). The API (#79) keeps readings append-only in the database too, uses built-in adult ranges for a hospital that has set none (`db:seed` gives the clinic its own), and attaches a token's readings to the encounter `encounter.opened` names. Notes: `apps/web/src/features/triage/CLAUDE.md`, and for the API `apps/api/src/features/triage/CLAUDE.md`.
- **OPD consultation (web, #80; API #86):** "Start consultation" on the token being served (`queue.row.actions`) and on today's appointment (`appointment.row.actions`, `appointment.detail.actions`, now given `patientId`), the consultation at `encounters/:encounterId` with `TriageSummary`, notes kept as drafts on the server as they are written then signed or amended, diagnoses (ICD-10 through `CodeSearch`, words, or both; retracted with a reason), prescriptions (#81: medicines from the catalog through `DrugSearch`, with dose, route, frequency, days, quantity and instructions, warnings of a listed allergy and of a medicine already prescribed, and revising), printing a prescription and the visit summary under the hospital's letterhead (address, phone and registration number from the tenant config), with the prescriber's qualifications and registration number and a signature line, saying on the page what is missing (#397), each print recorded in the audit log first (#89), lab orders (#82: tests and panels from the catalog through `LabTestSearch`, with a priority and instructions, their status in words, a warning of one already in effect, and cancelling with a reason; no results yet, #92), imaging and procedure orders (#87: services of that category through `ServiceSearch`, otherwise as lab orders; no reports yet), closing and cancelling, the consultations list at `encounters`, and a "Clinical timeline" tab on the patient's screen (#83: the patient's visits newest first, a page at a time, filtered by type of visit and status; `GET /encounters` gained `type`). Behind the `clinical` switch, `encounter:read`, `encounter:create`, `encounter:update`, `clinicalNote:read`, `clinicalNote:write`, `diagnosis:read`, `diagnosis:write`, `prescription:read`, `prescription:create`, `encounter:print`, `order:read`, `order:create` and `order:cancel`; notes, diagnoses, prescriptions and orders are each hidden without their permission. Referrals (#88: to a department or one of its doctors, routine or urgent, with a reason; cancelled with a reason; `referral:read`, `referral:create`) and the follow-up panel of the `follow_ups` feature. Works at every width. Exports nothing yet. Diet orders have no screen yet; prescription templates and favourites are a later issue. Notes: `apps/web/src/features/clinical/CLAUDE.md`, and for the API `apps/api/src/features/clinical/CLAUDE.md`.
- **Follow-ups (web, #88; API in clinical):** the follow-up set on the consultation (a day today to a year ahead, a doctor, a note for the desk; one per consultation; cancelled with a reason) and the due list at `follow-ups`, in the navigation, from which the desk books one as an appointment of its patient, linked to it, with the appointments' free times; its state (to book, booked, attended, cancelled) is read from the appointment. Behind the `clinical` switch, `followUp:read` and `followUp:create`, and for booking `appointment:create` with the `appointments` switch. Works at every width. Exports `FollowUpPanel` (for the consultation). The appointments module exports `SlotPicker`, `bookableDays` and `useAppointmentsChanged` for it, and its API `bookAppointment`. Notes: `apps/web/src/features/follow-ups/CLAUDE.md`.
- **Laboratory (web, #90; API, #95):** the worklist at `lab`, in the navigation: the hospital's lab orders to collect, collected or received, stat first, filtered by priority; collecting a sample after checking the patient (name, MRN, date of birth), which gives it an accession id from the server (`YYMMDD-NNNN`, per hospital day) and prints its label with a Code 128 barcode, the print recorded in the audit log first; receiving it; and rejecting it with a reason, after which the order is collected again as a new sample. Behind the `laboratory` switch, `labSample:read`, `labSample:collect`, `labSample:receive` and `labSample:reject`. Works at every width. `PrintSheet` gained `className`, for something smaller than a page. Exports nothing yet. The API (#95) also enters, verifies and corrects results, append-only, each read against the reference range for the patient's sex and age on the day of collection, with `labResult:read`, `labResult:enter` and `labResult:verify`, and emits `lab.sample_collected`, `lab.sample_rejected`, `lab.critical_value` and `lab.result_verified`; it moves the order through `labOrder` and `moveLabOrder` from `features/clinical`, and reads the catalog through `labTestSample` and `analytesOf` from `features/lab-tests`. The result entry and report screens are #91 and #92. Notes: `apps/web/src/features/lab/CLAUDE.md`, and for the API `apps/api/src/features/lab/CLAUDE.md`.
- **Clinical (API only):** the encounter every clinical, ordering and billing record attaches to, opened as an OPD consultation from a queue token, an appointment or a walk-in, then closed or cancelled; notes drafted on the server, signed, and amended by a new note that keeps the old one; diagnoses (ICD-10 or text) recorded and retracted; one table of orders (lab, imaging, procedure, medication, diet) with its state machine; prescriptions whose lines are medication orders, revised by a new prescription (#86); referrals and follow-ups, booked as a linked appointment (#88). Behind the `clinical` switch, with `encounter:*`, `clinicalNote:*`, `diagnosis:*`, `order:*` and `prescription:*`; diagnoses are a permission of their own and the nurse's default view has no notes or diagnoses. Emits `encounter.opened`, `encounter.closed`, `encounter.cancelled`, `order.placed`, `order.cancelled`, `order.completed`, `referral.created`, `referral.cancelled`, `followup.created`, `followup.booked` and `followup.cancelled`. The catalogs gained exports for it (`diagnosisCode`, `orderableLabTest`, `orderableService`, `prescribableDrug`) and the queue `tokenForEncounter`. The web screens are the OPD consultation above; no charges yet (billing). Notes: `apps/api/src/features/clinical/CLAUDE.md`.
- **API (`apps/api`):** config, logging with redaction, the migration runner, tenancy with row-level security, cookie sessions with rotation, password sign-in with lockout and rate limit, invites, password reset, TOTP MFA, roles and permissions, the access guard, the notifier (SMTP), the audit log, the transactional outbox and job queue (pg-boss), per-tenant and per-user rate limits, idempotency keys, the registry of import kinds, live updates (`core/live`: a bus on Postgres `LISTEN`/`NOTIFY` and server-sent event streams that check the session again before sending) and the OpenAPI contract. Sixteen features besides health: `staff` (invitations, the staff list, deactivating, ending sessions), `patients` (search, register, duplicate check, read, update), `departments` (list, add, change, archive, restore), `doctors` (profiles, the staff a profile can be made for, weekly working hours), `services` (search, add, change, archive, restore, prices with effective dates, price lists), `drugs` (search, duplicate check, add, change, archive, restore), `lab-tests` (search, tests and panels, reference ranges, which range applies), `wards` (bed categories, wards, rooms, beds, blocking a bed) `codes` (the search, favourites, and the loader of a code set), `templates` (list, add, save a version, read a version, redact one, archive, restore), `imports` (batches, staging rows, the dry run and the commit as jobs, the report, the weekly expiry), `appointments` (the list, free slots, booking, one appointment, moving, cancelling, completing, a no-show), `queue` (issuing, checking in an appointment, the board, call-next, call again, skip, recall, priority, the event stream) `triage` (readings and corrections, the ranges by age, allergies) `clinical` (encounters, notes and amendments, diagnoses, orders, prescriptions, referrals, follow-ups) and `lab` (the worklist, samples, results with verification and corrections). Migrations `0001` to `0042`.

## Against the real API

- Works: sign-in (with the authenticator code step), the hospital picker and switcher, the access policy, sign-out, and the whole patients module: list and search, registration, the duplicate check, the patient screen and editing (`db:seed` adds 250 sample patients to each sample hospital), the departments screen (`db:seed` adds ten sample departments), the staff screen, the doctors screen (`db:seed` gives the sample doctors a profile with weekday morning hours), the services and prices screen (`db:seed` adds a sample price catalog), the drugs screen (`db:seed` adds sample medicines and consumables), the lab tests screen (`db:seed` adds sample tests, two panels and reference ranges), the wards screen (`db:seed` adds four bed categories and three wards with their rooms and beds) the codes screen (`db:seed` loads the two sample sets of `apps/api/sample-codes` and marks a few favourites) the templates screen (`db:seed` adds one template of each kind), the import centre (on for the sample hospital), the OPD queue with its live board (`db:seed` adds today's tokens), triage (`nurse@sample-hospital.test` records; a doctor only reads) the consultation (`db:seed` opens none: a doctor calls a token and starts one from it) and the laboratory worklist (on at the sample hospital: the lab orders a doctor places).
- Mock only: everything else. `notices`, change password, the account sessions and `POST /session/open-link` are in the planned contract (`packages/contract/planned.openapi.json`) with no backend yet, and the real policy lists only permissions the API knows (the staff, patient, department, doctor, service, drug, lab test, ward, code, template, import, appointment, queue, vitals, allergy, clinical and laboratory permissions so far), so other feature screens show "no access" there.

## Known gaps

- **The authenticator (two-step sign-in) is off for every hospital unless it is switched on.** Two per-hospital switches in `tenant_features` control it: `mfa` offers it to the staff (the set-up screen at `/security` and the link on the account page), and `mfa_required` with it makes it compulsory, which the server enforces (403 `mfa_required` on every route of the hospital until one is set up). There is no screen for the switches yet: they are set in the database or the seed until the platform admin module exists. There is no per-role requirement; that belongs with the roles API (#137).
- The account page (`/profile`) changes the password and ends other sessions against the mock only: its three endpoints are in the planned contract until #257.
- Disabling the authenticator and regenerating recovery codes have no screen yet (#252), and `/security` is reached from the account page only when no authenticator is set up.
- Not checked yet, although stated as targets in Responsive Design: Safari on iOS (every Playwright project is Chromium), full-screen dialogs on a phone, and a phone Lighthouse run.
- A hospital's address, phone and registration number (printed on the letterhead, #397) have no screen: they are set in the database or the seed until the platform admin module or a hospital settings screen exists.
- The dev seed runs only against a database on this machine; another host has to be named with `--allow-host` (see `apps/api/CLAUDE.md`).
- `pnpm audit` reports two moderate advisories in `react-router` 6, fixed only in 7.x. CI gates at high.
- Production needs `MFA_ENCRYPTION_KEY`, and the migrate step needs the same environment as the API (it also applies default role permissions).
