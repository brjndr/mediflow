# Nursing (web): module notes

What was decided for this module in the web app (#157, NR-01). The root `CLAUDE.md` wins where the two disagree. The API is `apps/api/src/features/nursing/CLAUDE.md` (#163); read it too.

## What exists

- **Worklist** at `/nursing` (`admission:read` and `nursingVitals:read`, `nursing` switch; the API also needs `admissions`): `GET /admissions?status=admitted` as a `DataGrid` (patient first, MRN masked), filtered by ward (`?ward=` in the address; the select is left out without `ward:read`). "Chart vitals" opens the stay.
- **Vitals chart** at `/nursing/:admissionId/vitals`: record a reading (`nursingVitals:record`; at least one measurement, systolic and diastolic together), correct one with a reason (a new reading; the corrected one stays in the table marked "Corrected" and is left out of the chart and the score), a trend chart (`TimeSeriesChart`, one measure at a time or the score), and the readings as a `DataGrid` with the API's low/high flags written as words. Only the newest 50 readings load first, more by "Load more"; the chart draws what is loaded. Writes are hidden for a stay that is not admitted.
- **Early warning score** (`ews.ts`): points from bands per measurement (systolic, pulse, temperature, SpO2: the NEWS2 bands as defaults), added up; `attention` at 5 or any one measurement at 3, `urgent` at 7. A level is a word and an icon. "Worsening" when the score rose by 2 or more since the reading before, or rose at each of the last three. Respiratory rate and consciousness are not charted, so it is a guide (the screen says so). Bands: min included, max excluded.

## Decisions and gaps

- **Configurable** means `EwsConfig` is a parameter of the scoring and `nursingSettingsSchema` (`settings.ts`) is ready, but it is not in the manifest (a `settings` entry adds a section to the admin settings screen, which would show an empty one) and tenant settings are not delivered to the web app yet, so `useEwsConfig()` returns the defaults. When the settings reach the tenant config, read them there; nothing else changes.
- **No "per nurse" list:** the API has no assignment of patients to a nurse; the worklist is per ward. A proposed follow-up.
- The mock keeps readings in `mocks/handlers/nursing.ts`, registered before the admissions handlers because `/admissions/:id/:action` there would otherwise answer the POSTs. Tests admit patients with `addMockAdmission` (`mocks/handlers/admissions-flow.ts`) and chart readings with `addMockWardVital`.
- Idempotency keys come from `hooks/use-nursing.ts`, one per request body.
- Not built (API has them): ward stock requests. Diet: see the end of this file.

## Medication chart (#158, NR-02)

- **Screen** `/nursing/:admissionId/mar` (`admission:read` and `mar:read`; charting needs `mar:record`), reached from "Medication chart" on the worklist. Doses due on a day (a date input, default today at the hospital) as a `DataGrid`, the entries on the chart below it (newest due first, "Load more"), the patient's allergies above.
- **The schedule is the web app's** (`mar-schedule.ts`): the API keeps no schedule, only an entry per order and `scheduledAt`, one per slot (409 `slot_recorded`). So the clock times a frequency is due are fixed in one table, in the hospital's timezone, the same for every device: `OD` 08:00, `BD` 08:00 and 20:00, `TDS` 06, 14, 22, `QID` 06, 12, 18, 22, `HS` 22:00, `1-0-1` by its number of parts, `q6h` every N hours from 06:00. An order with no times (as needed, `SOS`, anything not understood) is one row, "As needed", charted for the minute it is given. Making the times a hospital setting is a follow-up; until then a changed table would give different instants for the same dose, so change it with care. Slots before the order was placed are left out; the API refuses a slot more than 24 hours ahead, so those rows cannot be charted.
- **Dose checks** (`marFormSchema`): a given dose is typed, defaulting to the order's, and a dose that is not the ordered one needs a reason; anything but given needs a reason; amending always does. The server's rule on doses a day answers 422 `extra_dose_reason_required`, and the dialog then asks for the reason (the mock has the same rule).
- **Allergies:** read with triage's `useAllergies` (needs `allergy:read`; without it the screen says so and does not check) and matched to the medicine by clinical's `allergyCovers`. The match is by the order's `itemName`, as the order carries no generic name. A match shows an alert and the dose needs the nurse's confirmation. Charting is disabled until the allergies have loaded. It warns, never refuses.
- **Append-only:** nothing edits an entry. "Amend" adds a new entry for the same order and slot that names the one it amends, which stays in the list marked "Amended"; the amendment is marked "Amendment". An amended entry cannot be amended again (the API says 422).
- `not_dispensed` (nothing dispensed yet) is shown in the dialog before charting and in the status line after. It is a warning only.
- **Not built:** a witness for high-risk medicines, a patient or bedside barcode check, due and overdue doses on the worklist, a hospital-set schedule.
- The mock is `mocks/handlers/nursing-mar.ts` (`addMockMarOrder`, `addMockMarEntry`), spread first in `nursingHandlers`.

## Doctor rounds and progress notes (#159, NR-03)

- **Round list** `/nursing/rounds` (`admission:read` and `progressNote:read`), reached from a link on the worklist: the admitted stays of one doctor, from the new `doctorId` filter of `GET /admissions`. It opens on the signed-in doctor's own patients (the doctor whose `userId` is the session's, found in `useDoctorOptions`), "All doctors" for the rest; the choice is `?doctor=` in the address. Someone without `doctor:read` has no select and sees everyone the server's scope allows. Rows open the notes, vitals or medication chart.
- **Notes** `/nursing/:admissionId/notes`: add a note (type ward round, nursing or handover; `progressNote:write`), the notes newest first as a `DataGrid`, "Amend" and "History". Only the author amends (the action is `aria-disabled` for others; the server answers 403 `not_author`) and only while the patient is admitted. An amendment sends the `version` it started from; 409 `conflict` asks the person to reopen. Nothing is overwritten: the history dialog lists every version with author and time. The doctor now holds `progressNote:write` by default (API `permissions.ts`), which synchronises on the next `db:migrate`.
- **Orders from the ward** are not a new form: the stay's `encounterId` is given to clinical's `EncounterOrders` below the notes (lab, imaging and procedure orders, each panel with its own permissions). Medication orders from the ward are not offered (prescribing stays in the consultation); diet orders: see the end of this file.
- Note text is a single line of plain text as the API's pattern allows (no line breaks), up to 4000 characters. Allowing line breaks needs the API's `PlainLines` on the note body: a proposed follow-up.
- The mock is `mocks/handlers/nursing-notes.ts` (`addMockProgressNote`).

## Fluid balance and care plans (#160, NR-04)

- **Shifts** (`shifts.ts`): morning 06:00 to 14:00, evening 14:00 to 22:00, night 22:00 to 06:00, in the hospital's timezone, one fixed table like the medication times (making them a hospital setting is a follow-up). A "nursing day" starts with the morning shift, so the night belongs to the day it begins on. `shiftOf` names the shift of an instant: it is the "Shift" column of the progress notes, which is how the issue's "shift notes" are met (notes of kind nursing or handover already existed).
- **Fluids** `/nursing/:admissionId/fluids` (`admission:read` and `fluidBalance:read`; recording and correcting need `fluidBalance:record`): a date input (default today), a table of the three shifts and the whole day, then the entries of that nursing day as a `DataGrid`. **Totals are the server's** (`GET /fluids/totals?from&to`, one request for each shift, the day is the sum), never added up from the loaded page, so a long day still totals right. Intake is oral, intravenous, tube or other; output is urine, drain, vomit, stool or other. Whole millilitres, 1 to 5000.
- **Append-only:** nothing edits an entry. "Correct" adds an entry that names the one it corrects, keeps intake or output, and replaces it in the totals; the original stays in the list marked "Corrected", an entry is corrected once. Writes are hidden for a stay that is not admitted.
- **Care plans** `/nursing/:admissionId/care-plan` (`carePlan:read`, writing `carePlan:write`): plans as cards (not a `DataGrid`: each holds its own task list), each with its goal, tasks and a count of those done. Start a plan with a problem, an optional goal and first task; add tasks; "Mark done" once per task (nobody undoes it); end a plan as completed or cancelled, after which nothing in it changes. The mock is `mocks/handlers/nursing-care.ts` (`addMockWardFluid`, `addMockCarePlan`).
- **Not built:** due times on tasks in the form (the API takes `dueAt`, and the screen shows it), recurring tasks, a task assigned to a nurse, fluid targets or a restriction, balance on the worklist.

## Diet orders and the kitchen list (#161, NR-05)

- **Kitchen list** `/nursing/kitchen` (`admission:read` and `order:read`), linked from the worklist: the admitted patients as a `DataGrid` (patient first, MRN masked) with the diet each is on, its priority, status and time, filtered by ward (`?ward=`). It comes from the new `GET /diet/kitchen-list` (one request per page, never one per stay) and is read again every 30 seconds, so it follows the latest orders. A patient with no diet order reads "No diet order", never an empty cell.
- **Diet of a stay** `/nursing/:admissionId/diet` (the "Diet" row action): the stay's diet orders (`GET /admissions/{id}/diet`, newest first, the live newest one marked "Current diet" in words) and, with `order:create` while the stay is admitted, a form placing a diet order on the stay's encounter (`POST /encounters/{id}/orders`, type `diet`, instructions up to 500 characters, priority routine or urgent). A new order replaces the diet; there is no editing or cancelling here (cancelling is clinical's `order:cancel`, no screen yet). Nurses get no `order:create` by default, so they read; a doctor places.
- **The diet is free text** (the API's order has only instructions): no diet type catalog, no meal times, no allergy or restriction check. Proposed follow-ups: a diet type list, kitchen printing, marking a meal served.
- The mock is `mocks/handlers/nursing-diet.ts` (`addMockDietOrder`), registered before the clinical mock because a ward stay's encounter is not one the clinical mock holds; other order types fall through to it.

## Ward care tests (#162, NR-06)

- `e2e/nursing.spec.ts` runs the ward flow at three widths: chart vitals (an urgent score), place a diet order, chart a dose, write a round note, plus the vitals form by keyboard alone. A lab order from the ward is not in the flow: the clinical mock does not know a ward stay's encounter.
- To give the browser a medication order, the mock accepts `POST /encounters/{id}/orders` with `type: 'medication'` on a ward stay (`marOrderHandlers` in `mocks/handlers/nursing-mar.ts`, registered through `dietHandlers` so it comes before the clinical mock). Use frequency `SOS` in a spec: it is one "As needed" row at any hour.
- Playwright reuses a server already on port 4173 (`reuseExistingServer`), so another checkout's stale build can answer; check the port before trusting a local run.
