# Lab tests: module notes

What this module is and what was decided for it. The root `CLAUDE.md` holds the rules every module follows, and it wins where the two disagree. Keep this file current with the module.

## What exists

**Lab tests (web and API):** the tests and panels the laboratory offers: code, name, section, sample and container, turnaround time, unit, and the laboratory service of the price catalog each is charged as. A panel is an ordered set of single tests. A numeric test has reference ranges by sex and age, with optional critical limits, and a check of which range applies to a patient of an age and a sex (#64). Behind the `lab_tests` switch and the `labTest:read` and `labTest:manage` permissions. Desktop-only. Decided for now: a result is a number or text, and text has no range; an age limit is kept as it is typed, a value with a unit (days, weeks, months, years), as HL7 FHIR and other hospital systems do, and never turned into a count of days; a patient reaches it on the calendar day that lies that long after the date of birth, so leap years and the lengths of months are respected and a patient changes range on the birthday (`features/lab-tests/age.ts`, which the mock shares; #286); a range runs from an age, included, until an age, not included; a range for one sex is used before a range for anyone, and a patient recorded as other gets only a range for anyone; two ranges for the same people can never both hold, whatever the date of birth, so limits in months or years against limits in weeks or days are refused unless no date of birth can bring them together, and ranges that meet give the same age in the same unit; a test that a panel in use is made of cannot be archived; critical limits are recorded here and acting on them is the laboratory's (M8).

The API (#300) is described in `apps/api/src/features/lab-tests/CLAUDE.md`. It holds a copy of `age.ts`, and a test there fails when the two files differ: change both together. Where it differs from the mock: tests are in the order the database gives their lower-cased names, not the browser's; a `code` or a `kind` sent with a change is dropped, not refused; a limit sent as null or as text is refused, never read as 0, and one of a thousand million or more is refused; text is stored tidied (one normal form, single spaces), and a control character, a zero-width space or a direction override in it is a 400, which the form checks too, with a message of its own (`PLAIN_TEXT` of `shared/utils/text.ts`); a test is newly linked only to a service that is not archived; the Idempotency-Key is optional; and a body the schema refuses is a 400 before the test is looked for.

Decided with the API, and the mock does the same: a test that has reference ranges keeps its unit until they are removed, as it stays numeric (409 `lab_test_has_ranges`), because the ranges are numbers in that unit; a panel takes no result type or unit on a change either; and a panel one of whose tests is archived is not restored (409 `lab_test_component_archived`, for which this screen has no message of its own yet and shows the general one).

## Decided

- **Single tests can be loaded from a file (#68),** through the import centre (`features/imports`), each charged as the laboratory service of the code given (`serviceCode`). Panels and reference ranges are not: they are made here. `POST /lab-tests` and the import both use `features/lab-tests/create.ts` in the API.

## Known gaps

- The lab test screen picks the service a test is charged as from the price catalog (`POST /services/search`), so linking one needs `service:read` and the `services` switch as well. Without them the link is shown and cannot be changed there.
- Nothing keeps the link to a service true afterwards: the service can be archived or given another category, and the test stays linked. It matters when charges are posted (M11).
- A critical limit is checked against the one normal limit a range has: a range with only an upper limit accepts a critical low below it, which says that a value is normal and critical at once. The rule is this form's, the mock's and the API's alike (#310).
- The lookup of a reference range on the catalog screen takes an age someone typed and identifies no patient (the age is tried as that of a person born on 1 January 2001). For a real patient the laboratory module (M8) works the range out on the server from the date of birth and the date the sample was collected, with the same calendar rule, and never sends an age or a date of birth in an address. Ranges by hours of life (bilirubin in a newborn) need a time of birth, which the patient record does not hold yet.
