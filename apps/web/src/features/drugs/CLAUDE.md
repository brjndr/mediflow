# Drugs and consumables: module notes

What this module is and what was decided for it. The root `CLAUDE.md` holds the rules every module follows, and it wins where the two disagree. Keep this file current with the module.

## What exists

**Drugs and consumables (web and API):** what each medicine and consumable the hospital keeps is (generic name, brand, form, strength, unit, drug schedule, controlled or not, tax class, reorder level), in one list with a type; server search on every word, filters for type, form, schedule and controlled drugs, and an archived view; adding with a warning when the list has the same generic name in the same form, and a refusal for exactly the same item; editing with a version check (#63). Behind the `drugs` switch and the `drug:read` and `drug:manage` permissions. Desktop-only. Decided for now: no price and no stock here (a selling price goes with the batch, in the pharmacy); the schedule is recorded as a class, and what each schedule requires is the pharmacy module's to enforce; Schedule X and narcotic items are always controlled.

The API (#299) is described in `apps/api/src/features/drugs/CLAUDE.md`. Where it differs from the mock: items are in the order the database gives their lower-cased names, not the browser's; and a change of schedule or of the controlled flag is audited as `reclassify`, not `update`.

## Decided

- **The trace of a controlled item (#306).** An item can leave a controlled schedule without a `reclassify` entry: archive it, and add a near-identical one (another spelling of the strength) with no schedule. No single request breaks a rule, so nothing is refused. Instead the API writes a second audit entry, `beside_controlled`, whenever an item that is not controlled is added, or renamed or moved to another form, while the hospital has a controlled item of the same generic name in the same form, archived or not. Whoever reviews the audit log finds every such item under one action. It goes by the `controlled` flag, not the schedule, and it never blocks: paracetamol with and without codeine is a real pair. The form already warns of items with the same generic name and form before adding.
- **No `drug:reclassify` permission for now (#306).** By default only the admin holds `drug:manage`, and a separate permission for the schedule and the controlled flag would mean little unless adding beside a controlled item needed it too. To be taken up with role management (M14) if a hospital wants the two split.
- **Text is plain and tidied (#306, #322).** The form refuses a control character and anything that prints as nothing (Unicode's default ignorable code points: the zero-width space, the soft hyphen, the direction marks and overrides, the word joiner, the tag characters and the like) with a message of its own (`validation.plain_text`), as every catalog form does, through `PLAIN_TEXT` of `shared/utils/text.ts`. The joiners Indic scripts need (U+200C, U+200D) are allowed, and the variation selectors of emoji right after an emoji.
- **An item is compared with the others without the Indic joiners (#322).** They are allowed and kept as typed, but many places print them as nothing, so a name with one and the same name without it are the same item: the refusal of exactly the same item, the warning of the same generic name and form, and the `beside_controlled` trace all compare the stored key columns of migration 0031 (`generic_key`, `brand_key`, `strength_key`).
- **No lock for a controlled and an uncontrolled item added at the same moment (#322).** Two requests that add a controlled and an uncontrolled item of the same generic name and form at once do not see each other, so the trace is not written. Decided: no lock. The trace is there for a sequence (archive a controlled item, then add it again without its schedule), which is two requests one after the other, and those see each other. Two items added at once by two people each have their own `create` entry, under their own names, and a review of the controlled items finds both. A lock would cost every add and rename, and an import of a file of drugs, which is one transaction, would hold one per row: thousands of advisory locks in one transaction run out of the database's lock table. Revisit with the pharmacy module (M10) if it ever reads the trace as a rule.
- **Items can be loaded from a file (#68),** through the import centre (`features/imports`), each checked, audited and traced beside a controlled item as `POST /drugs` does: both use `features/drugs/create.ts` in the API. Change a create rule there.
