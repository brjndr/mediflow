# Import centre: module notes

What this module is and what was decided for it. The root `CLAUDE.md` holds the rules every module follows, and it wins where the two disagree. Keep this file current with the module.

## What exists

**Import centre (web and API):** services and prices, drugs and consumables, single lab tests and patients loaded from a CSV file (#68). The file is read in the browser, in a Web Worker, and its columns are matched to the fields of the kind (by their titles where they can be). A file that is not UTF-8 is refused (its letters would be damaged). The rows are sent to a batch in chunks of at most 1,000 rows and about 800 KB, and sending stops, mid-request too, when the screen is left or the hospital changes, and a job checks every row the way that kind's create route checks a request, writing nothing: the dry run. Its report gives the line, the field and a code for each problem. A checked batch with no problems is written by a second job in one transaction, so it is written whole or not at all. Behind the `imports` switch and the `import:read` and `import:run` permissions, the admin's by default. Desktop-only (the bulk import centre is on the list in the root `CLAUDE.md`).

The API is described in `apps/api/CLAUDE.md`, under Import centre. Where it differs from the mock: the mock checks only what the conversion of a row finds (a required field left empty, a value not of its type, a duplicate within the file), never what the catalog already holds, and a written batch adds nothing to the other features' mock lists.

## Decided

- **Loading a kind needs what adding one record of it needs.** `import:run` and that kind's own permission (`service:manage`, `drug:manage`, `labTest:manage`), with its module on. Patients need `patient:create` and `patient:import`, the admin's alone by default, and every patient written is audited as a registration is. `GET /imports/kinds` lists what the person may load, so the screen offers nothing else.
- **A kind is registered by the feature that owns it** (`app.importKinds.register` in its plugin, with its columns, its body schema and a `prepare` and a `write`). The import centre knows no kind of its own. A catalog becomes importable without a change here, apart from its words in `locales` (a kind the app has no words for is not offered).
- **The route and the import write a record through the same functions** (`create.ts` in each of `services`, `drugs`, `lab-tests` and `patients`), so an imported record is checked, tidied, audited and announced exactly as one added on its screen. The audit entries of a batch carry `import:<batch id>` where a request's carry the request id, and the actor is who asked for the batch to be written.
- **All or nothing, and checked twice.** The dry run reads only, and takes no lock, so a hospital keeps working while it runs. The commit checks each row again before writing it, because the catalog may have changed since: one refusal rolls everything back and the batch fails with its report (`rows_refused`). A database refusal while writing (a code taken by another request at that moment) ends the writing, and the rows are then checked again without writing so that the report is whole. A patient batch holds the MRN counter until it commits: a registration at the desk meanwhile waits three seconds and is then told to try again (503 `busy`), rather than holding a connection every hospital shares. Patient files are a go-live task.
- **One batch is written at a time at a hospital** (409 `import_running`, a unique index), and the person's permissions are checked again when each job starts, the dry run's too (`permission_withdrawn`).
- **The rows can be patient data,** so they are deleted when the batch is written, fails or is given up, and an hourly job gives up a batch left staged or checked for a week (`expired`) and one whose job stopped (`stalled`: no sign of life for an hour), which also frees the hospital to write the next. The report holds codes, never a value of the file, so it is shown to anyone with `import:read`, whatever the kind (a patient batch's codes say which lines were refused, not who is on them). A failed job keeps only a code in the job queue's own table, never the error, whose text could quote a row. Nothing of the file is kept in the browser beyond the screen.
- **A patient row with the name and date of birth of someone registered, or of an earlier row of the file, is refused** (`patient_possible_duplicate`, `duplicate_in_file`), not registered a second time: the file is corrected first. The desk's other match, a shared phone number, is not a refusal here, since a family often shares one phone and could otherwise never be loaded. Merging records that turn out to be one person is MR-03.
- **Contact consent is not loaded from a file.** It is a decision of the patient's, recorded with when and by whom; an old system's column says neither, and the import would record the importer as having captured it. It is asked at the next visit.
- **Lab tests are single tests**, charged as the laboratory service of the code given (`serviceCode`). Panels and reference ranges are made on the catalog screen. Naming the service by its code needs no `service:read`: whoever may load tests learns only which laboratory codes exist, which is catalog data. **Services** take a first price on the standard list from today, as an amount in the hospital's currency (`1250.50` or `1,250.50`; `12,50` is refused).
- **The screen follows a working batch by asking,** soon at first and then less often (one second, growing to five), until the job ends. SSE is not built yet.

## Known gaps

- No download of the report as a file: it is read on screen, a page at a time. Official exports are generated on the server, so this waits for object storage and signed URLs.
- Staff stay with their own invitation from a file (up to 200, `features/staff`), since each one sends an email. Wards and code sets are not imported here: wards are few, and code sets are loaded by an operator (`codes:load`).
- No undo of a written batch: each record is changed or archived on its own screen.
- A job that stops without ending (the process killed) leaves its batch working until the next delivery takes it over (after ten minutes without a heartbeat) or the hourly job gives it up (after an hour).
- A row is validated by Ajv against the kind's schema with options of its own, not by Fastify's compiled validator: a keyword the routes' validator treats differently would be a difference between the screen and the import. The schemas today use none.
