# Consents and certificates (web): module notes

What was decided for MR-02 (#190). The root `CLAUDE.md` wins where the two disagree. Read `features/documents/CLAUDE.md` too: this tab sits beside the documents tab.

- **A tab, nothing else.** `ConsentsTab` is contributed to `patient.detail.tabs` behind the `consents` switch. No route, no navigation item. The tab shows when the caller has `consent:read` or `certificate:read`, and then only the list they may read. `consent:sign` and `certificate:issue` add the buttons.
- **The API does not exist yet.** The endpoints are in `packages/contract/planned.openapi.json` (`/patients/{id}/consents`, `/consents/{id}`, `/patients/{id}/certificates`) and are mocked in `mocks/handlers/consents.ts`. When the API is built, delete them from the planned file. Records are NOT the documents module's `consent` and `certificate` categories: those are scanned files; these are data. A later issue may also store a rendered PDF as a document.
- **Immutable by construction.** There is no update or delete endpoint, no edit action and no retire. A mistake is a new consent or certificate. The screen says so before signing and when reading one.
- **A consent keeps the text it was signed with.** The form reads the newest version of a `consent` template (`useTemplateChoices`, so it needs `template:read` and the `templates` switch), fills it with `fillPlaceholders` (patient name and MRN, hospital, the signed-in user as `doctor.name`, today, the typed procedure) and shows it. The filled text and the template id and version go in the request, so a later change to the template never changes a signed consent. A placeholder that could not be filled (the patient's name, MRN, age and sex are all filled, the last two from `usePatientAgeSex` of the patients index) blocks signing: what is signed is what is seen.
- **Signature capture.** `SignaturePad` is an SVG that records pointer strokes as path data (`M x y L x y`, a 300 by 150 box, at most 20000 characters), no canvas and no image. The path is checked against `[ML0-9 .,-]` before it is drawn from the API. A pad cannot be used with a keyboard, so "Type the name instead" is the other method: the signer's name and a confirmation that they agree. Both are recorded with `signatureMethod`. A guardian or representative can sign (`signerRole`).
- **Certificates.** Four kinds: medical, fitness, birth, death. The fields of each kind are a fixed list in `schemas.ts` (`CERTIFICATE_FIELDS`); the form and the zod schema are made from it, and the API stores them as a string map. The server numbers them. **Not done: "hospital-configured formats".** The field lists are fixed in code; configuring them per hospital needs a template kind `certificate` (or a settings record) in the API and the templates module, proposed as a follow-up.
- **Idempotency.** One key per identical body (`useAttempt`), so a second tap on a slow answer is the same request.
- **Printing (#568):** "Print" beside "Close" on an opened consent or certificate (`PrintRecord.tsx`): the record on the letterhead in a `PrintSheet`, with the patient, signature and who printed it. Client only, no extra audit call (the read is audited by the API when built). Not done: a server-made PDF stored as a document, which needs the API.
- **Not built:** witness signatures, withdrawing a consent (a new record, once the rules are decided), a tablet-handover signing mode, and the API.
