# Patients: module notes

What this module is and what was decided for it. The root `CLAUDE.md` holds the rules every module follows, and it wins where the two disagree. Keep this file current with the module.

## What exists

**Patients (web and API):** the list with server-side search, sort and cursor paging; registration with a duplicate check while typing and on saving; the patient screen, which hosts the `patient.detail.tabs` and `patient.detail.actions` slots; editing with optimistic save and conflict detection; a field-level permission for contact details (`patient.contact:read`); deep links to a patient; audit of every read and write, and the `patient.registered` and `patient.updated` events. Exports `PatientSearch` (#71), the box another feature's screen chooses a patient with (booking an appointment): the term goes in the body of `POST /patients/search`, nothing is asked for until something is typed, and an option shows the name, the MRN and the date of birth, to tell two patients of one name apart. It needs `patient:read` and the `patients` switch, and says so without them. Exports `usePatientName` (#76): the name and MRN of a patient another feature's screen was given the id of (issuing a queue token from the patient's screen), from the same query as the patient's screen, so coming from there asks for nothing again; the rest of the record is not passed on. The caller checks `patient:read` and the switch first.

## Decided

- **Patients can be registered from a file (#68),** through the import centre (`features/imports`), with `patient:import` (the admin's alone by default) as well as `patient:create`. Each is given an MRN, audited and announced as a registration at the desk is (`features/patients/create.ts` in the API, which `POST /patients` uses too). A row with the name and date of birth of someone registered is refused, not registered twice; a shared phone number is not a refusal there, since families share phones. Contact consent is never taken from a file: it is asked at the next visit. While a batch is written, a registration at the desk waits three seconds for the MRN counter and is then answered 503 `busy`.

- **The patient screens are worked with the keyboard and a screen reader (#345).** Every form is the form kit's, so a failed submit focuses the first field to fix and required fields say so. The Edit action says "Saving your changes…" and then "Your changes were saved." from a status region that is always there, since one added with its text already in it may not be read; a refused save says nothing there, as the screen's alert says it. The duplicate suggestions were already a region of that kind. How many patients the list holds is said by the screen's own status, not by the grid (#340).

- **Merging a duplicate (#558, MR-03).** `patients/:id/merge` (`patient:read` and `patient:merge`) keeps the record in the path and merges a chosen one into it: the duplicate is found with `PatientSearch`, both records are shown side by side with the rows each module would move (`GET /patients/{id}/merge-preview`, #603; a module adds a label to `merge.modules`, an unlabelled one shows its name; the mock modules register counters with `registerMockMergeCounter`), a reason is required, and a confirm dialog comes before the request. It goes with both versions read and an idempotency key kept for an identical resubmit; the answer's per-module counts are shown. The action ("Merge a duplicate") and the "Merge history" tab (`GET /patients/{id}/merges`) are contributed to the patient screen's slots by this feature, for `patient:merge`; a merged record shows a notice with a link to the record to use. Not built: unmerge and correction requests (no API yet).

## Known gaps

- Patient search finds a name by its exact letters, in any word order. It does not find a misspelled name; that needs the search design in #259.
- Patient search matches text against the hospital's rows without a trigram index, because row-level security keeps Postgres from using one (see `apps/api/CLAUDE.md`). It is fast at tens of thousands of patients per hospital; a very large hospital needs a dedicated search design.
