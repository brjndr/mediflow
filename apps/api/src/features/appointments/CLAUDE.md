# Appointments API

What was decided for this feature's API (#75). Claude Code loads it when a file of this folder is read. The web side's notes, which hold the rules the screens and this API share, are in `apps/web/src/features/appointments/CLAUDE.md`.

- **`features/appointments`** is a patient booked with a doctor of the same hospital, from one instant to another, then moved, cancelled, completed or marked a no-show. Behind the `appointments` module flag, with `appointment:read` (admin, doctor, nurse, receptionist), `appointment:create` and `appointment:update` (admin, receptionist), the roles table of `docs/PRODUCT.md`. It implements what `planned.openapi.json` held for the web app (#70 to #73), with the same names and codes.
- **Instants in UTC, days at the hospital.** `starts_at` and `ends_at` are `timestamptz`. A day in a request (`from`, `to`, `day`) is a calendar day at the hospital, turned into instants in SQL with the tenant's timezone (`(day)::timestamp at time zone tz`), never in Node and never in the server's zone. The list gives the appointments that start on its days; one that runs past midnight is on the day it starts.
- **The database decides double booking.** Two exclusion constraints on the scheduled appointments, `appointments_doctor_free` (`tenant_id`, `doctor_id`, `tstzrange`) and `appointments_patient_free` (the same for the patient), both with the hospital in them. Half-open ranges, so one appointment may end as the next begins. A violation (SQLSTATE 23P01) is read by the constraint's name: `slot_taken` or `patient_overlap`. Of simultaneous bookings, the second waits for the first's transaction and is refused when it commits; the concurrency tests prove it. Cancelled and no-show appointments are outside the constraints, so they free their time.
- **A start must be a slot of the doctor's hours,** on that day at the hospital, not started, and within today to 90 days ahead (422 `outside_hours`). The check takes every working slot, free or not, and leaves "is it free" to the constraints, so a held time is 409 `slot_taken`, not 422. `GET /appointments/free-slots` gives only the free ones. The slot length is the profile's `consultation_minutes` at the moment of booking; a later change of length does not move booked appointments.
- **A doctor is bookable while practising** (the profile and the membership active, as `features/doctors` defines it). Free slots answer 404 `not_found` for any other; booking and moving answer 422 `unknown_doctor`. A patient of another hospital and one that does not exist are the same 422 `unknown_patient`.
- **References carry the hospital:** `(tenant_id, patient_id)` and `(tenant_id, doctor_id)`. Migration 0034 added `patients_tenant_id_id UNIQUE (tenant_id, id)` for it, as 0017 did for doctors. `appointments_tenant_id_id` is there for encounters (M7).
- **Final is final in the database too.** The guard trigger refuses any update of a completed, cancelled or no-show appointment, and of its hospital, id, patient and booking details; it counts `version`. The rules that depend on the clock (`too_early` before the start for complete and no-show, `too_late` after the end for cancel) are checked in the handler on the locked row, against the database's `now()`. No DELETE for the app role.
- **Scope of `appointment:read`, `appointment:create` and `appointment:update`:** `all`; `own`, the appointments of the caller's own doctor profile; `department`, those of the departments the caller's active profile is in. Someone without a profile sees nothing under either. A booking is made, and a move goes, only to a doctor the caller's scope of `appointment:create` or `appointment:update` reaches (422 `unknown_doctor` otherwise), so nobody makes an appointment they could not then see. Outside the scope is the same 404 `appointment_not_found` as another hospital's, and the list gives an empty page, never a refusal. A change applies the scope of `appointment:update`; the free slots need either `appointment:create` or `appointment:update`, which the guard cannot say, so the route declares `permissions: []` and checks the policy itself.
- **Idempotency keys are required** on booking and every change, and nothing of an answer is kept (`idempotent: { body: 'none', required: true }`), because each names a patient. A repeated booking is answered from the appointment found by `request.idempotentId`; a repeated change does nothing and answers with the appointment as it is now. Either is a read of the record, audited as `read` (the core audit hook writes what a repeat's handler records). The contract marks the header required (`RequiredIdempotencyHeaders`), so a request without it is a 400 `validation_failed`.
- **Reasons and notes are plain text of several lines** (`PLAIN_LINES`, `tidyLinesOptional`), as the web app's text areas allow.
- **A day the clocks change:** a slot is offered only when its start and its end are both the wall times they say, so a wall time that does not exist (clocks forward) and a slot that would cross the change are left out. When the clocks go back, the repeated hour is offered once. No Indian hospital has a change; the rule is for a timezone that has one.
- **Moving to the same doctor and time is allowed** and counts as a move (a new version and an `appointment.rescheduled` event), as the mock does. The web app offers only the free times, which never list the appointment's own.
- **Migration 0034 adds a unique constraint on `patients`** in the same transaction, which locks the table while it builds: harmless before a pilot. On a large table, a later migration of this kind builds the index `CONCURRENTLY` in a no-transaction file, then adds the constraint `USING INDEX`.
- **Audit:** booking `create`, every change `update`, the record and every row of a list page `read`, all with the appointment's id. **Events** carry ids and codes only: `appointment.created` (patient, doctor, start), `appointment.rescheduled` (the old and new doctor and start, the reason code), `appointment.cancelled` (the reason code), `appointment.completed` and `appointment.no_show`. A move's note is not kept anywhere; a cancellation's reason and note are on the record.
- **`extensions` is refused when it has any part** (422 `unknown_extension`): no feature registers fields for the booking form yet, and nothing of it is stored. The first feature that does adds a registry of schemas (as `app.importKinds` is one) and a place to keep the values; the body schema is a plain object because a body may not give a schema for unnamed properties (`core/http/strict-body.ts`).
- **Seed:** `db:seed` books every other slot of each practising doctor from three days ago to a week ahead at each sample hospital, once.
