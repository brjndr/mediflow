# Operations API

What was decided for this feature's API (BE-30, #200). Claude Code loads it when a file of this folder is read. No web screens yet (OP-01 to OP-04, #195 to #198; tests in #199).

- **One folder, four modules.** `features/operations` holds rosters, the blood bank, ambulances and bed cleaning tasks, each behind its own hospital switch: `roster`, `bloodbank`, `ambulance`, `housekeeping`. Migration 0079 (the tables have `tenant_id` defaulting to `app_tenant_id()`, row-level security as usual).
- **Permissions:** `roster:read|manage`, `bloodUnit:read|manage|issue`, `ambulance:read|manage|dispatch`, `cleaningTask:read|work|manage`. A move route that has several targets (blood unit, cleaning task) declares the lowest permission and checks the one the move needs in the handler (`requireGrant`, 403 `permission_denied`).
- **Roster:** a shift is at most 24 hours; one person has no two scheduled shifts that overlap (exclusion constraint, 409 `shift_overlap`). A shift is only cancelled (once, a trigger), never edited or deleted; cancelling frees the time. The person must be a member of the hospital.
- **Blood bank:** `collected -> testing -> available -> reserved -> issued -> transfused`; `discarded` (a reason required) from any state before transfusion; `expired` for an available or reserved unit past its date; `reserved -> available` releases. The table is in `BLOOD_TRANSITIONS` and again in the `blood_units_guard` trigger, so SQL cannot skip a step either; the trigger also refuses reserving or issuing a unit past its date. Every move is a row in the append-only `blood_unit_events`. Testing, clearing and discarding are `bloodUnit:manage` (the bank); reserving, issuing, transfusing and releasing are `bloodUnit:issue` (the ward). A patient is named by id only, never a name; reserving needs a patient the caller may read. Nothing moves a unit to `expired` by itself yet: a person records it (`not_expired` otherwise).
- **Ambulances:** a trip goes `requested -> dispatched -> picked_up -> completed`, or `cancelled` before the pick-up. Dispatching names an available ambulance and sets it `on_trip`; ending or cancelling the trip frees it. A partial unique index gives an ambulance one live trip. `out_of_service` and back is `POST /ambulances/{id}/service`, only from `available`. A trip's patient is optional (an emergency with no record). Pick-up and destination are plain text, not looked at beyond length.
- **Cleaning tasks:** `open -> in_progress -> done` or `cancelled`. Finishing a task moves its bed from cleaning to available, under the ward's lock and announced on the beds stream (it needs the `wards` module). The subscriber to `bed.released` makes a `discharge` task for the bed when the hospital has `housekeeping` on (one live task per bed, a repeat event does nothing). A `routine` task is asked for with `POST /cleaning-tasks` for an available (set to cleaning) or cleaning bed. `bed:update` housekeeping in admissions still works on its own; finishing a task on a bed already marked ready by hand just completes the task.
- **Idempotency:** creates require an `Idempotency-Key`; moves accept one. Responses hold no patient name, so the roster, blood bank, ambulance fleet and cleaning keep the whole answer; a trip request keeps only its id.
- **Events (ids and codes):** `roster.shift_scheduled`, `roster.shift_cancelled`, `blood.unit_registered`, `blood.unit_status_changed`, `ambulance.trip_requested`, `ambulance.trip_status_changed`, `cleaning.task_created`, `cleaning.task_completed`. The outbox event name allows letters only before the first dot, which is why they are not `blood_unit.*`.
- **Not here (proposed follow-ups):** the web screens (#195 to #198) and tests (#199); crossmatching, blood donors, screening results and a patient's blood group; a job that expires units on their date; a roster that repeats (templates, weekly patterns), swaps and leave; ambulance crew, mileage, GPS and charging a trip; assigning a cleaning team and its shifts; charging blood units to the encounter.
