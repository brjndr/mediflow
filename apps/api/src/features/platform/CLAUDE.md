# Platform administration (API)

What was decided for `/platform/*` (BE-15, #132). The rules for the role are in `docs/ARCHITECTURE.md`, "Hospital onboarding rules". The screens are built in M13 (PL-01 to PL-07), as far as the web notes say.

## What it is

- **Routes for the product's operators only:** `config: { access: 'platform' }` (`core/platform/plugin.ts`). The caller must be an active user with `users.is_platform_admin` **and** a confirmed authenticator; otherwise 403 `forbidden` (not a platform admin, whatever a hospital role holds) or 403 `mfa_required`. The flag is read from the database on every request, so removing it takes effect at once. Setting up the authenticator is a session route and stays within reach.
- **No tenant, no `request.tx`.** Database work goes through `withPlatformTransaction` (`core/platform/db.ts`), which runs as the role `mediflow_platform` (migration 0065) and sets no tenant. A platform admin has no membership anywhere, so a hospital's own routes answer 409 `no_active_tenant`, and naming a hospital in a session gives nothing.
- **The role's grants are the boundary.** `mediflow_platform` can read and change `tenants` (named columns) and `tenant_features`, and add roles' default grants; read `roles`, a hospital's head count (`memberships`: four columns) and invites (everything but `token_hash`); and add or withdraw an invite. It has **no grant** on any table with patient, clinical or billing data, nor on `users`, `sessions` or `audit_log`. `platform.test.ts` lists the tables it holds grants on and fails if one is added without a decision. Do not widen the role to make a feature easier: add a SECURITY DEFINER function that answers the one question.
- **The platform's own trail** is `platform_audit_log` (append-only, trigger-enforced), written in the same transaction as the change. Rows hold ids and codes only (`detail`: a module id, a count, a list of field names), never a hospital's name or any value. `hospital_id` is deliberately not called `tenant_id` and has no foreign key: the row is the platform's, and the trail outlives the hospital.
- **Idempotency for creates** is the platform's own (`platform_requests`, keyed by user and key), because core/idempotency is scoped to a hospital. `POST /platform/hospitals` requires the key; only the hospital's id is kept, and a repeat answers with the hospital as it is now.

## Routes

| Route                                                                                  | Does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /platform/hospitals`                                                             | Creates a hospital active, with its built-in roles (a trigger), their default permissions (`syncRoleDefaults`) and the modules named.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `GET /platform/hospitals`, `GET /platform/hospitals/:id`                               | Cursor list (newest first, filter by status or part of a name or slug) and one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `PATCH /platform/hospitals/:id`                                                        | Configuration, with `version`; 409 `version_conflict`. Never the status or the modules.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `PUT /platform/hospitals/:id/features`                                                 | Module flags, and the `mfa` and `mfa_required` switches. A name no feature declares is 400 `unknown_feature`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `POST /platform/hospitals/:id/admin-invite`                                            | The first admin, role `admin`: only while the hospital is active and has **no active admin** (409 `hospital_has_admin`), and never to a platform admin's address (`is_platform_admin_email`, a definer function: the role has no grant on `users`). Otherwise a platform admin could invite themselves into a live hospital and read its data, which the role exists to prevent. The trail records the address's domain and a short hash, not the address. Saved with a hash that matches no token; the existing email job gives it its token (`core/auth/emails.ts`) after the commit. Only for an active hospital. |
| `GET /platform/hospitals/:id/admin-invites`, `POST .../admin-invites/:inviteId/revoke` | The open invites of a hospital (not accepted, not withdrawn, newest first, at most 50, expired ones included, never a token), and withdrawing one (404 for an invite that is not open at that hospital; the trail records `hospital.admin_invite_revoked` with ids only). **Sending again is inviting the same address again:** the invite route withdraws the earlier one to that address.                                                                                                                                                                                                                          |
| `POST .../suspend`, `.../reactivate`, `.../offboard`                                   | Status changes: `active` ⇄ `suspended`; `offboarding` from either; back to `active` by reactivate. Suspend and offboard withdraw open invites in the same transaction and end the hospital's sessions at once (best effort: the tenancy hook already refuses the hospital, and the offboarding job sweeps again).                                                                                                                                                                                                                                                                                                    |
| `GET /platform/audit` (filters: `hospitalId`, `actorId`)                               | The trail, by cursor, optionally for one hospital (`hospitalId`) or one actor (`actorId`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

## Decisions

- **Suspended and offboarding block the same way:** the tenancy hook answers 403 `tenant_suspended` for any status but `active`, so staff who are signed in lose access on the next request, and `GET /session` shows the status for the web app to draw the page.
- **Offboarding schedules, it does not delete.** It sets `offboarding_requested_at` and `delete_after`, withdraws open invites and ends sessions, and the `platform.offboard` job (ids only, repeatable, a no-op once reactivated) sweeps again for anything that slipped in, adding to the trail only when it changed something. The export and the deletion are not built, and nothing deletes a hospital's data. They belong with the hardening milestone, as a job on `mediflow_worker` that waits for `delete_after`.
- **No plan tiers.** A hospital has module flags and two limits (`max_users`, `storage_mb`); a plan table would invent pricing. **`max_users` is enforced (#462)** by `core/tenancy/limits.ts`: `POST /invites` and reactivating a member refuse with 409 `user_limit_reached` when active members plus open invitations would pass it (null: no limit). A new invite to an address that already has an open one takes no further place, and an open invite to an active member's address is not counted twice. The check runs under an advisory lock for the hospital, so two requests cannot take the last place together (the app role cannot lock the `tenants` row). `GET /tenant` shows `staffLimit: { max, used }` to any member; the session's copy of the tenant does not carry it. **`storage_mb` is still not enforced:** it belongs with the file store's S3 adapter, which does not exist yet.
- **Modules are the features that declare permissions** (`app.permissions.all()`), plus the two authenticator switches. A module with no permissions cannot be switched from here until it has one.
- **Text is tidied** (`core/http/text.ts`), and the locale, zone and currency are checked against the runtime's own lists, so a typo is refused instead of stored.
- **The seed triggers run as the table owner** (`tenants_seed_roles`, `tenants_seed_price_list` are SECURITY DEFINER, with `pg_temp` last in the search path), as `bump_policy_revision` already does. Those tables force row-level security with policies for the app role only, so this relies on the migrating login bypassing it (a superuser or BYPASSRLS, as in development and CI). Check that against the production database login before the first hospital is created there.
- **Idempotency keys** are swept as they are met (older than 24 hours are deleted in `claimKey`), so there is no job.
- **Rate limit:** platform routes use the per-route limit (per address, `RATE_LIMIT_USER_PER_MINUTE`), since the per-hospital limits need a hospital.

## The first platform admin

`pnpm --filter api platform:bootstrap --email=<address> --name="<name>"` (or `node dist/core/platform/bootstrap-cli.js` in the image), on the owner connection. It creates the account with a password nobody knows and prints a 24-hour set-password link to the terminal only. The person chooses a password, signs in, and must confirm an authenticator before any platform route answers. Run again for the same address it makes a new link (a lost account). It refuses an address that belongs to hospital staff. There is no API route or screen for it, by design.

## Break-glass access (design only, not built)

Platform admins get no patient data by default. If support must ever look at a hospital's data, the design is:

1. **The hospital's admin grants it,** not the platform: an admin of that hospital creates a grant naming the platform user, a reason and a duration (at most 24 hours), kept in a tenant table `support_access_grants` (`tenant_id`, `granted_by`, `platform_user_id`, `expires_at`, `revoked_at`). The platform cannot create or extend one, and the admin can revoke it at any time.
2. **It opens a hospital session, not a wider platform role.** While a grant is open the platform user may switch into that hospital with a synthetic membership in a read-only role `support` (built in to every hospital with no default grants; the grant lists the permissions allowed, read permissions only). Everything then goes through the normal tenant transaction, RLS, access guard and audit; nothing bypasses them, and `mediflow_platform` stays as narrow as it is.
3. **It ends by itself:** the session's lifetime is capped at the grant's expiry, and every request checks that the grant is still open (as event streams re-check their caller).
4. **Everything is visible to the hospital:** each read is in the hospital's own `audit_log` with the platform user as actor, flagged as support, and the hospital's admin sees a list of grants and the access made under each. The grant, its use and its end also go to `platform_audit_log`.
5. **No writes** under `support`, and MFA is checked again when the grant is opened.

It needs a hospital-side screen and the role management API (BE-16), so it is built after them, as its own issue.
