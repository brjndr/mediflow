# Platform administration (API)

What was decided for `/platform/*` (BE-15, #132). The rules for the role are in `docs/ARCHITECTURE.md`, "Hospital onboarding rules". The screens are built in M13 (PL-01 to PL-07), as far as the web notes say.

## What it is

- **Routes for the product's operators only:** `config: { access: 'platform' }` (`core/platform/plugin.ts`). The caller must be an active user with `users.is_platform_admin` **and** a confirmed authenticator; otherwise 403 `forbidden` (not a platform admin, whatever a hospital role holds) or 403 `mfa_required`. The flag is read from the database on every request, so removing it takes effect at once. Setting up the authenticator is a session route and stays within reach.
- **No tenant, no `request.tx`.** Database work goes through `withPlatformTransaction` (`core/platform/db.ts`), which runs as the role `mediflow_platform` (migration 0065) and sets no tenant. A platform admin has no membership anywhere, so a hospital's own routes answer 409 `no_active_tenant`, and naming a hospital in a session gives nothing.
- **The role's grants are the boundary.** `mediflow_platform` can read and change `tenants` (named columns) and `tenant_features`, and add roles' default grants; read `roles`, a hospital's head count (`memberships`: four columns) and invites (everything but `token_hash`); and add or withdraw an invite. It has **no grant** on any table with patient, clinical or billing data, nor on `users`, `sessions` or `audit_log`. `platform.test.ts` lists the tables it holds grants on and fails if one is added without a decision. Do not widen the role to make a feature easier: add a SECURITY DEFINER function that answers the one question.
- **The platform's own trail** is `platform_audit_log` (append-only, trigger-enforced), written in the same transaction as the change. Rows hold ids and codes only (`detail`: a module id, a count, a list of field names), never a hospital's name or any value. `hospital_id` is deliberately not called `tenant_id` and has no foreign key: the row is the platform's, and the trail outlives the hospital.
- **Idempotency for creates** is the platform's own (`platform_requests`, keyed by user and key), because core/idempotency is scoped to a hospital. `POST /platform/hospitals` requires the key; only the hospital's id is kept, and a repeat answers with the hospital as it is now.

## Routes

| Route                                                                                  | Does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /platform/hospitals`                                                             | Creates a hospital active, with its built-in roles (a trigger), their default permissions (`syncRoleDefaults`) and the modules named.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `GET /platform/hospitals`, `GET /platform/hospitals/:id`                               | Cursor list (newest first, filter by status or part of a name or slug) and one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `PATCH /platform/hospitals/:id`                                                        | Configuration, with `version`; 409 `version_conflict`. Never the status or the modules.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `GET /platform/modules` (#468)                                                         | The ids a hospital can be given: `{ items: [{ id, kind }] }`, `kind` `module` (sorted) or `switch` (`mfa`, `mfa_required`). Built from the same lists `PUT .../features` and the create route check, so they cannot drift; ids and kinds only, no names.                                                                                                                                                                                                                                                                                                                                                             |
| `PUT /platform/hospitals/:id/features`                                                 | Module flags, and the `mfa` and `mfa_required` switches. A name no feature declares is 400 `unknown_feature`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `POST /platform/hospitals/:id/admin-invite`                                            | The first admin, role `admin`: only while the hospital is active and has **no active admin** (409 `hospital_has_admin`), and never to a platform admin's address (`is_platform_admin_email`, a definer function: the role has no grant on `users`). Otherwise a platform admin could invite themselves into a live hospital and read its data, which the role exists to prevent. The trail records the address's domain and a short hash, not the address. Saved with a hash that matches no token; the existing email job gives it its token (`core/auth/emails.ts`) after the commit. Only for an active hospital. |
| `GET /platform/hospitals/:id/admin-invites`, `POST .../admin-invites/:inviteId/revoke` | The open invites of a hospital (not accepted, not withdrawn, newest first, at most 50, expired ones included, never a token), and withdrawing one (404 for an invite that is not open at that hospital; the trail records `hospital.admin_invite_revoked` with ids only). **Sending again is inviting the same address again:** the invite route withdraws the earlier one to that address.                                                                                                                                                                                                                          |
| `POST .../suspend`, `.../reactivate`, `.../offboard`                                   | Status changes: `active` ⇄ `suspended`; `offboarding` from either; back to `active` by reactivate. Suspend and offboard withdraw open invites in the same transaction and end the hospital's sessions at once (best effort: the tenancy hook already refuses the hospital, and the offboarding job sweeps again).                                                                                                                                                                                                                                                                                                    |
| `GET /platform/audit` (filters: `hospitalId`, `actorId`)                               | The trail, by cursor, optionally for one hospital (`hospitalId`) or one actor (`actorId`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

## Decisions

- **Suspended and offboarding block the same way:** the tenancy hook answers 403 `tenant_suspended` for any status but `active`, so staff who are signed in lose access on the next request, and `GET /session` shows the status for the web app to draw the page.
- **Offboarding schedules, it does not delete.** It sets `offboarding_requested_at` and `delete_after`, withdraws open invites and ends sessions, and the `platform.offboard` job (ids only, repeatable, a no-op once reactivated) sweeps again for anything that slipped in, adding to the trail only when it changed something. The export (#960) and the deletion (#961) are in the next two sections.
- **No plan tiers.** A hospital has module flags and two limits (`max_users`, `storage_mb`); a plan table would invent pricing. **`max_users` is enforced (#462)** by `core/tenancy/limits.ts`: `POST /invites` and reactivating a member refuse with 409 `user_limit_reached` when active members plus open invitations would pass it (null: no limit). A new invite to an address that already has an open one takes no further place, and an open invite to an active member's address is not counted twice. The check runs under an advisory lock for the hospital, so two requests cannot take the last place together (the app role cannot lock the `tenants` row). `GET /tenant` shows `staffLimit: { max, used }` to any member; the session's copy of the tenant does not carry it. **`storage_mb` is still not enforced:** it belongs with the file store's S3 adapter, which does not exist yet.
- **Modules are the features that declare permissions** (`app.permissions.all()`), plus the two authenticator switches, and `GET /platform/modules` lists them (a test checks every listed id is accepted). A module with no permissions cannot be switched from here until it has one.
- **Text is tidied** (`core/http/text.ts`), and the locale, zone and currency are checked against the runtime's own lists, so a typo is refused instead of stored.
- **The seed triggers run as the table owner** (`tenants_seed_roles`, `tenants_seed_price_list` are SECURITY DEFINER, with `pg_temp` last in the search path), as `bump_policy_revision` already does. Those tables force row-level security with policies for the app role only, so this relies on the migrating login bypassing it (a superuser or BYPASSRLS, as in development and CI). Check that against the production database login before the first hospital is created there.
- **Idempotency keys** are swept as they are met (older than 24 hours are deleted in `claimKey`), so there is no job.
- **Rate limit:** platform routes use the per-route limit (per address, `RATE_LIMIT_USER_PER_MINUTE`), since the per-hospital limits need a hospital.

## Offboarding export (#960)

Decided in #959 (`docs/OPEN_DECISIONS.md`). Offboarding queues an export at once; `POST /platform/hospitals/:id/exports` makes another (409 `export_in_progress` while one is queued or running, `hospital_not_offboarding`), `GET .../exports` lists them.

- **The registry is `tenant-data.ts`:** every table with `tenant_id`, as exported plain, exported with a treatment (columns left out, a column naming a stored file) or not exported with a reason. `export.test.ts` reads the catalog and fails when a table is in none of them, so a new tenant table cannot ship without a decision. The deletion (#961) uses the same registry (`deletedTables()`, and `deletionOrder` for the order).
- **The job (`platform.export`, `export.ts`) reads as the hospital:** the app role with the tenant set (`withTenantTransaction`, read only), so row-level security keeps another hospital's rows out; the platform role stays without grants on data. Each table is a CSV through a cursor (`tables/<table>.csv`, a null is an empty cell), plus `tables/_staff.csv` (the people the rows name), `hospital.json`, the stored files as they are (`files/<key>`, from `report_runs`, `imaging_images` and `patient_documents`) and `manifest.json` with a SHA-256 for every entry and the list of files the store no longer had. One tar archive, `exports/<hospitalId>/<exportId>.tar`, whose checksum is on the row. Credentials (`invites.token_hash`, `import_batches.claim_token`) are left out.
- **The archive is streamed** (#973): the tables' CSVs are held in memory (ceiling `EXPORT_TABLES_MAX_BYTES`, 1.5 GB, past it the run ends `failed` with `too_large`), the stored files are read one at a time and the tar goes to the file store through `putStream` (`core/files/store.ts`: a temporary file renamed on disk, a multipart upload on S3), with its size and SHA-256 worked out as it passes, so the archive has no ceiling. A stream that fails leaves no file. The download route sends the file as a stream too (`getStream`). A failed run is not retried by itself; ask again.
- **`tenant_exports` is the platform's table** (migration 0135, no `tenant_id`, no foreign key, like the trail). An export counts as made when a row of the hospital has `status = 'succeeded'`, and as downloaded when `first_downloaded_at` is set (`download_count`, `last_downloaded_at`); the deletion reads both.
- **The link is emailed, never returned** (#974): `POST .../exports/:exportId/email-link` with `adminUserId` (409 `not_a_hospital_admin`, `export_not_ready`, `hospital_not_offboarding`) writes `hospital.export_link_issued` to the trail and queues the `platform.export-link-email` job (ids only), then answers 202 with no link, so the operator never holds it. The job (`export-link.ts`) looks the export, the hospital and the admin up again (`offboarding_admin_contacts`; nothing is sent for an admin who lost the role) and sends the `export_link` email, whose link is made at that moment and lasts 7 days. The signature covers the export and that admin. `GET /offboarding-exports/:exportId` has no session (the hospital is closed, so its staff have none): the link is the credential, and every refusal is one 404. It checks again that the hospital is still offboarding and the admin still active, and writes `hospital.export_downloaded` to the platform trail with the admin as actor. The platform sends another during the grace period. The link is under the web origin's `/api` prefix, as the proxy strips it. Whoever holds the email can download, so the mail says not to forward it.

## Deleting an offboarded hospital's data (#961)

Decided in #959. Migration 0136: `tenant_deletions` (the platform's table, no foreign key, ids, codes and counts only) and the tenant status `deleted`.

- **Routes:** `POST /platform/hospitals/:id/deletion` asks (body `{ waiverReference? }`), `.../deletion/approve` is the second platform admin's, `.../deletion/cancel` withdraws a request that has not started, `GET .../deletion` shows the latest. Reactivating the hospital cancels an open request (audited as `hospital.deletion_cancelled`, reason `reactivated`), and is refused with 409 `deletion_running` once the job has started.
- **The rules** (`deletionBlocker` in `deletion.ts`, checked at the request, at the approval and again by the job): the hospital is offboarding (`hospital_not_offboarding`), `delete_after` has passed (`grace_period_not_over`), a made and downloaded export or a waiver reference (`export_not_downloaded`), no unreleased legal hold (`legal_hold`) and no medico-legal case that is not yet disposed of (`medico_legal_open`). All 409. Nothing deletes on a timer: the approver must differ from the requester (`approver_must_differ`, and a CHECK in the table).
- **The waiver is a reference only** (`waiver_reference`, a document number, 80 characters): the signed paper is kept by the platform's operators, not in this database.
- **The job (`platform.delete`, `runDeletion`)** takes an advisory lock for the deletion id on a connection it holds for the whole run (a live run is never taken over, a dead one frees it), claims the approved row, then in ONE transaction on the owner connection: locks the `tenants` row and the deletion row (reactivate takes the same `tenants` lock first), reads every rule again, reads the keys of the stored files (`report_runs`, `imaging_images`, `patient_documents`, the hospital's own export archives) and refuses any key not in `<kind>/<hospital id>/` (`verification_failed`), refuses if a table outside the registry has a foreign key into it (replica mode would leave orphans), deletes every table of the registry (children before parents), clears `sessions.active_tenant_id`, **checks every table with a `tenant_id` column is empty of the hospital** (`verification_failed`, whole transaction rolls back), switches the session back to normal triggers, and writes the tombstone, the deletion row (with `file_keys`) and the trail. **Only after that commit are the files deleted** and checked gone (`files_deleted_at`, trail `hospital.deletion_files_deleted`): a file cannot be brought back, so none is touched while the rows can still roll back. A failure there leaves the keys on the row and `sweepDeletions` (`platform.delete-sweep`, every 15 minutes) finishes them; it also sends again an approved request whose job was lost. Each step goes to `platform_audit_log`; a failure is logged with ids and a code only, and marked `failed` (trail written only by the run that failed it). A failed run is not retried by itself; a new request needs a new approval. The request and approval trail rows carry the waiver reference.
- **It runs with `session_replication_role = replica`** so the append-only triggers (the audit log, stock ledger, signed notes) do not refuse, which needs a database login that is a superuser or has been granted SET on that parameter (`GRANT SET ON PARAMETER session_replication_role TO <login>`, PostgreSQL 15). This is the one place records are removed; every request still meets the triggers. Check it against the production login before the first deletion. The job uses the API's own pool (`app.database.pool`), as the export does; a separate worker login is not built.
- **The tombstone:** the `tenants` row stays with status `deleted` and `deleted_at`, its name and slug (so an id and a slug are never reused), and the address, phone, registration number, GSTIN and logo cleared. `tenant_exports`, `tenant_deletions` and the platform trail stay. A deleted hospital cannot be reactivated, suspended or offboarded again.
- **Accounts (#997):** after the rows, in the same transaction, the job deletes the `users` of this hospital's members who now have no membership anywhere (never a platform admin, never an account that did not belong here); their sessions, authenticator and tokens follow by cascade. A person of two hospitals stays. The count is `accounts` in the `hospital.deleted` trail entry. Backups hold the data until they rotate out (about 35 days), as stated to the hospital.
- **Web:** the hospital page shows the export and the deletion and offers request, approve and cancel (#996); a `deleted` hospital has no actions.

## The first platform admin

`pnpm --filter api platform:bootstrap --email=<address> --name="<name>"` (or `node dist/core/platform/bootstrap-cli.js` in the image), on the owner connection. It creates the account with a password nobody knows and prints a 24-hour set-password link to the terminal only. The person chooses a password, signs in, and must confirm an authenticator before any platform route answers. Run again for the same address it makes a new link (a lost account). It refuses an address that belongs to hospital staff. There is no API route or screen for it, by design.

## Break-glass access (design only, not built)

Platform admins get no patient data by default. If support must ever look at a hospital's data, the design is:

1. **The hospital's admin grants it,** not the platform: an admin of that hospital creates a grant naming the platform user, a reason and a duration (at most 24 hours), kept in a tenant table `support_access_grants` (`tenant_id`, `granted_by`, `platform_user_id`, `expires_at`, `revoked_at`). The platform cannot create or extend one, and the admin can revoke it at any time.
2. **It opens a hospital session, not a wider platform role.** While a grant is open the platform user may switch into that hospital with a synthetic membership in a read-only role `support` (built in to every hospital with no default grants; the grant lists the permissions allowed, read permissions only). Everything then goes through the normal tenant transaction, RLS, access guard and audit; nothing bypasses them, and `mediflow_platform` stays as narrow as it is.
3. **It ends by itself:** the session's lifetime is capped at the grant's expiry, and every request checks that the grant is still open (as event streams re-check their caller).
4. **Everything is visible to the hospital:** each read is in the hospital's own `audit_log` with the platform user as actor, flagged as support, and the hospital's admin sees a list of grants and the access made under each. The grant, its use and its end also go to `platform_audit_log`.
5. **No writes** under `support`, and MFA is checked again when the grant is opened.

It needs a hospital-side screen and the role management API (BE-16), so it is built after them, as its own issue.

- **Deletion job deployment notes (#995):** the run holds one pooled connection for its advisory lock and takes more for the transaction, so keep the `platform.delete` worker concurrency below the pool size (it is 1). The lock is session-scoped, so it needs a direct connection, not a transaction-mode pooler such as PgBouncer. Files whose removal keeps failing stay on the row (`file_keys`) and the sweep retries every 15 minutes, logging `hospital_deletion_files_pending` each time. After `MAX_FILE_ATTEMPTS` (20, about five hours) the row gets `files_stuck_at`, the sweep skips it and `platform_audit_log` gets one `hospital.deletion_files_stuck` row (#1001) for an operator. To retry after fixing the store, clear `files_stuck_at` and set `file_attempts` to 0 on the `tenant_deletions` row.

## Deletion reminders (#998)

Decided in #959: the hospital's admins are told 30 and 7 days before `delete_after`. Migration 0142.

- **The job** `platform.deletion-reminders` (`deletion-reminders.ts`) runs daily at 05:00 UTC. For each offboarding hospital with `delete_after` in the next 30 days it picks one reminder by the whole days left (`reminderDue`: 7 or fewer is the 7 day reminder, up to 30 the 30 day one), so a hospital offboarded with fewer than 30 days left is never told "30 days". Nothing is sent once the date has passed (the deletion is by request and approval) or the hospital is reactivated.
- **Who:** the active admins of the hospital (`offboarding_admin_contacts(hospital)`, a SECURITY DEFINER function, since the platform role has no grant on `users`; never a platform admin). Template `deletion_reminder`: hospital name, days left, the date in the hospital's time zone; no link and no data. It does not carry the export link: the platform issues that (`export-routes.ts`).
- **Idempotent per person:** `deletion_reminders` (platform's table, ids and times only, primary key hospital, person, reminder, `delete_after`) gets a row after the mail server took the email. A repeated run sends nothing again; a failed send is thrown after the rest were tried and the queue repeats the job, which writes only to those without a row. A crash between send and row can repeat one email, never skip one. A new `delete_after` (reactivated then offboarded again) is reminded afresh. The platform trail is not written: it needs an actor and a job has none.
