# Triage API

What was decided for this feature's API (#79). Claude Code loads it when a file of this folder is read. The web side's notes, which hold the rules the screens and this API share, are in `apps/web/src/features/triage/CLAUDE.md`.

- **`features/triage`** is a patient's vital signs and chief complaint, the normal ranges they are marked against, and the patient's allergies. Behind the `triage` module flag, with `vitals:read` and `allergy:read` (admin, doctor, nurse; the pharmacist also reads allergies, for the warning as a medicine is dispensed, #100) and `vitals:record` and `allergy:update` (admin, nurse), the "Triage and vitals" row of `docs/PRODUCT.md`. It implements what `planned.openapi.json` held for the web app (#77), with the same names and codes.
- **Readings are append-only in the database.** The app role may INSERT and SELECT `vitals`, and UPDATE only `encounter_id`; a trigger refuses any other change, and setting it twice. A correction is a new row with `corrects_id` and a reason (`vitals_correction`), and the partial unique index `vitals_corrected_once` lets a reading be corrected once, also between two corrections sent at the same moment (read as 422 `already_corrected`). A correction takes the token and the encounter of the reading it corrects, on the server.
- **The limits of a body are checks of the table** as well as the route's schema, and blood pressure goes together with the diastolic below the systolic (`vitals_blood_pressure`). One decimal is checked in the handler (`toFixed(1)`), since JSON Schema's `multipleOf` is not exact for decimals. Temperature, weight and height are `numeric(…, 1)` and read back as numbers (`::float8`).
- **A token is taken only when it is this patient's and today's at the hospital,** in any status (a re-check after the consultation), else 422 `token_not_for_patient`.
- **Ranges (#378, #379, migration 0070):** `vital_ranges` is append-only (the app may insert and select): a row is a band (`infant` under 1 year, `child` 1 to 11, `adolescent` 12 to 17, `adult` 18 and over), a measure, the limits and `effective_from`. The ranges in force at a moment are, for each band and measure, the newest row not after it; a row with neither limit means the measure is not checked, and no row means the built-in range of the band (`DEFAULT_RANGES`, a starting point for a hospital's clinicians to review). Rows that existed before the migration are adult rows effective from the epoch. The band is chosen from the patient's whole years of age at the hospital's own date (`bandOf`, `dateAt`).
- **`GET /vitals/ranges`** (`vitals:read`) gives the table as it stands with a `version` (how many times it was saved), **`PUT /vitals/ranges`** (`vitals:configure`, admin) saves the whole table from that version, in effect from now: another save first is 409 `conflict`, saves are serialised per hospital with an advisory lock, a low limit not below its high one or a limit with a second decimal is 422 `invalid_range`. Both are audited (`vital_ranges`, without an id). `GET /patients/{id}/vital-ranges` gives the patient's band today, audited with the patient id as it tells their age band.
- **A reading is answered with its `flags`** (`high` or `low` for each ranged value), computed on read from the ranges in effect at its `recorded_at` and the patient's band that day: nothing is stored on the reading, which stays append-only, and an edit of the ranges changes no earlier mark. A list loads the ranges once for its page.
- **Allergies** are one row per patient (`allergy_lists`), replaced whole: from version 0 an insert that does nothing when a row exists, from any other an update `where version = $v`, so of two saves at once the second is 409 `conflict` and changes nothing. No row is `unknown`. Every version is also written to `allergy_list_versions` (migration 0037) in the same transaction, which the app may only insert into and read, so what was removed, when and by whom stays known. Items are a JSON list checked by the route and the table (`none` with none, `listed` with 1 to 50), their text tidied. No idempotency key: the version does that job.
- **The allergen catalog (#380, migration 0066)** is the table `allergens` (name, kind `drug_class`, `food` or `other`, and for a class the lower-case generic names it covers, `members`). It is reference data shared by every hospital: it holds nothing about a patient or a hospital, so it has no `tenant_id` and no row-level security, and the app role may only read it (changing it is a migration; a hospital's own entries would be an additive table). A single medicine is not in it: `POST /allergens/search` (`allergy:read`, the `triage` flag, a body search, not audited) merges the catalog with the generic names of the hospital's own medicines (`medicineGenerics` from `features/drugs`, each name once, archived and consumables left out), in name order with one cursor (name, source, id). Both sources are ordered and compared `COLLATE "C"`, as the handler merges them bytewise, so a database whose locale orders punctuation differently cannot skip or repeat a name between pages (the drugs side sorts the hospital's matching medicines; it is asked only once something is typed). No `total`.
- **A coded allergy is stored as a snapshot.** An item of the list may name `allergenId` or `drugId` (not both; 422 `unknown_allergen` for one the hospital cannot use, a medicine of another hospital included, 400 for both); the server stores the catalog's name, the `kind` (`drug`, `drug_class`, `food`, `other`) and `members` (a class's members, or the medicine's generic name in lower case), so the list answers with what was known when it was saved and the catalog or the drug master may change or archive later without altering it. An item already on the list under the same id is kept as recorded when the list is saved again, so editing a reaction never fails over a medicine archived since. A medicine's member is its generic name normalised as the web app reads a medicine's names when it matches (lower case, anything but letters, digits and hyphens turned into spaces: "Paracetamol (Acetaminophen)" is stored as "paracetamol acetaminophen"), so it matches itself; the whole name is the member, so an allergy to a combination ("amoxicillin + clavulanic acid") does not flag the single ingredient, which is the class's job. Free text stays valid and has none of these fields. The scope check comes before any lookup.
- **Scope:** every route finds the patient within the scope of its own permission (`vitals:read`, `vitals:record`, `allergy:read`, `allergy:update`) through `patientInScope` from `features/patients`, which decides what `own` and `department` mean. A patient outside it, of another hospital, or of none, is 404 `not_found` on every route, as is a reading of another patient.
- **The token check is the queue's** (`tokenOfPatientToday` from `features/queue`): triage does not read `queue_tokens` itself.
- **Audit:** `vitals` (`create` when recorded, `read` for the record, every row of a page, and a repeated recording), `allergy_list` (`read`, `update`) and `vital_ranges` (`read`), with the patient id for the last two. **Events:** `vitals.recorded` (the reading, patient, token and corrected reading when there are) and `allergy.updated` (patient and new version, never the allergies), through the outbox.
- **`encounter.opened`:** the module's subscriber sets `encounter_id` on the readings of the token in the event's payload (`queueTokenId`; the encounter is the event's entity id) that have none, so a repeated event changes nothing. The clinical module emits it when an encounter opens from a token, with `queueTokenId` in its payload (#86), and `vitals.encounter_id` references `encounters` from migration 0039. A reading taken outside the queue still gets no encounter.
- **Idempotency keys are required** on recording, and only the new id is kept, so a repeat answers with the reading as it is.
- **Seed:** `db:seed` gives the clinic its own adult ranges (a temperature high from 37.5 °C, SpO₂ low below 94) and adds `nurse@sample-hospital.test`, who records; the sample doctor only reads.
- **Exports for nursing (#163):** `VITAL_LIMITS`, `VITAL_MEASURES`, `ageBasis`, `loadRangeRows` and `flagsFor` from `index.ts`, so ward vital signs use the same limits and are flagged against the same ranges by age band. Ward readings are their own table (`ward_vitals`), never a row of `vitals`.
