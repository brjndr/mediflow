# Laboratory API

What was decided for this feature's API (#95, BE-19). Claude Code loads it when a file of this folder is read. The web side's notes, which hold the rules the worklist and this API share, are in `apps/web/src/features/lab/CLAUDE.md`.

- **`features/lab`** is the worklist of lab orders, their samples and their results. Behind the `laboratory` module flag. It implements what `planned.openapi.json` held for the worklist and samples (#90), with the same names and codes, and adds the results API that result entry (#91) and reports (#92) build against.
- **Permissions and defaults** (the "Lab (collect, result, verify)" row of `docs/PRODUCT.md`): `labSample:read` and `labSample:collect` for the nurse, the lab technician and the admin; `labSample:receive`, `labSample:reject`, `labResult:enter` and `labResult:verify` for the lab technician and the admin; `labResult:read` for the doctor, the lab technician and the admin. The admin holds all, as in the clinical module (`grantsWithin`).
- **Only the scope `all` reaches anything.** The laboratory works the whole hospital's orders, so a role given a lab permission at `own` or `department` sees an empty worklist and the same 404 as another hospital's record. A doctor's `own` results is the change if a hospital asks for it (the encounter's scope, as the clinical module reads it).
- **The state machine is split across three records,** each with its own rules in the handler and a trigger: the order (`placed -> accepted -> in_progress -> completed`, the clinical module's), the sample (`collected -> received`, `collected | received -> rejected`) and each result (`entered -> verified`). Collecting accepts an order that was only placed; the first result entered moves it in progress; verifying the last current result completes it, with `order.completed`. The sample's status keeps the planned contract's three values: "resulted" and "verified" are the results' state, not the sample's.
- **The laboratory never writes the orders table.** It reads a lab order and moves it on through `labOrder` and `moveLabOrder` from `features/clinical` (its index), which audit the order and emit `order.completed`. The worklist reads the orders, patients and the test catalog in SQL, as the follow-up due list reads appointments. Cancelling stays the doctor's (`order:cancel`, from placed or accepted), so an order is never cancelled once a result is entered.
- **Every change locks the order first, then the sample** (`labOrder` with `forUpdate`, then the sample `for update`), so collecting, receiving, rejecting, entering, verifying, correcting and the doctor cancelling take their turn on one row. Two collections at the same moment are a 201 and a 409 `already_collected`, and the partial unique index `lab_samples_one_standing` is the backstop.
- **Accession ids** come from `lab_accession_counters`, one row per hospital and day, incremented by `INSERT … ON CONFLICT DO UPDATE` in the statement that takes the number, as the queue's tokens are. Four digits, more past 9999 in a day.
- **A sample names its order, encounter, patient and test together** (a foreign key to `orders (tenant_id, id, encounter_id, patient_id, lab_test_id)`, a unique constraint migration 0042 adds), and a result its sample, order, encounter and patient together, so nothing can be filed under another patient or visit. A sample's sample type and container are the catalog's when collected (`labTestSample` from `features/lab-tests`).
- **Results are append-only.** A result is never changed apart from being verified once (a trigger), and never removed (no DELETE grant). A correction (`POST /lab/results/:id/amend`) is a new result of the same sample and test, with the whole value and a reason, `amends_id` naming the one it replaces; a result is corrected once (`lab_results_amended_once`, 409 `already_amended`), so the history of a test is one line. The current result of a test is the one nothing amends (`amendedById` absent). A correction is entered, so it needs verifying again; the order stays completed meanwhile.
- **A result is entered for a received sample only** (a trigger too), and a sample is never rejected once it has a result (409 `has_results`, and the trigger). One first result per test of a sample (`lab_results_one_first`, 409 `already_resulted`).
- **What is resulted** is the test ordered, or each test of the panel ordered, as the catalog has them now (`analytesOf` from `features/lab-tests`). The code, name, unit and type are copied onto each result, so a report reads the same after the catalog changes.
- **A number is kept with its decimals** (`numeric`, so `5.10` stays `5.10`; leading zeros go, `007` is `7`): a decimal of one to nine digits, a point and up to six decimals, so `.5` is refused (422 `invalid_number`). It is read against the band for the patient's sex and age on the calendar day at the hospital the sample was collected (`bandFor`), and the band is copied onto the result, since a test's ranges are replaced as a set. The flag reads the critical limits first, then the normal range (`results.ts`), so a range that contradicts itself (#310) still gives one flag. No band, no flag. A correction is read against the band the replaced result kept.
- **What completes an order is the test as the catalog has it at verification:** every test of the panel now has a current verified result. A panel changed between collection and verification therefore waits for a test added meanwhile, and does not wait for one removed. Accepted: a panel is rarely changed, and keeping what a sample was to be resulted as is a column on the sample if a hospital needs it.
- **Only the laboratory moves a lab order while the hospital has it switched on:** the clinical module's `POST /orders/:id/status` refuses a lab order then (409 `lab_order`), since completing it there would complete it with no result, which could then never be entered. With the laboratory off, that route moves lab orders as before (a hospital that sends its tests out).
- **The worklist is read through `orders_tenant_lab_open`** (the open lab orders) and sorts the page in memory by priority, which holds while a hospital's open lab orders are a few hundred. A larger backlog needs a stored priority rank in the index; that is a follow-up, measured before the pilot.
- **Verifying names the results the verifier read** (`resultIds`): each must be current and entered, else 409 `conflict`. The person who entered a result may verify it (decided for #95: a small laboratory often has one technician on duty); requiring a second person is a per-hospital setting when one asks.
- **Idempotency keys are required** on every POST, and nothing of an answer is kept (`body: 'none'`). Collecting and correcting set `request.idempotentId`; a repeat answers with the record as it is now, audited as a read. A repeated receive, reject, entry or verification changes nothing and answers likewise; a repeat whose record cannot be found is a 404, never done again. A label print records nothing more on a repeat.
- **Audit:** `lab_sample` (`create`, `update`, `read`, `print`) and `lab_result` (`create`, `update` when verified, `read`), with the record's id; the worklist and the results audit `read` of each order they show. **Events** carry ids and codes only, never a value: `lab.sample_collected` (sample, order, encounter, patient, test, accession id), `lab.sample_rejected` (with the reason code), `lab.critical_value` (the result, sample, order, encounter, patient, test and flag, when a critical result is entered or a correction is critical) and `lab.result_verified` (the sample, order, encounter, patient, test and current result ids, each time every test of the order is verified, so again after a correction is verified).
- **Unverified results are withheld from a reader who can neither enter nor verify (#91).** `GET /lab/orders/:id/results` gives such a caller (the doctor's default `labResult:read` alone, or `labResult:enter`/`labResult:verify` at a narrower scope) only verified results, and names in `awaitingVerification` the tests whose current result is entered and not verified. A result being corrected keeps its replaced, verified result in the list (it names a correction that is not there), so the doctor sees it is history and that a new one is waiting. Only results given are audited. The holders are read from the policy (`request.access.policy()`), since `scope()` throws for a permission the route does not declare. Critical values still reach the doctor's side through `lab.critical_value`, whose alert is another module.
- **The results answer heads itself (#91):** the patient's name and MRN, the test as ordered and its priority, so the page needs no `patient:read` (a lab technician has none).
- **The completed stage (#91):** `GET /lab/worklist?stage=completed` lists completed lab orders, the newest completed first (`status_changed_at`, index `orders_tenant_lab_completed`, migration 0043), with no `total` since they only grow. It is how a verified result is found again to be corrected. Every row says how many of its current results are entered (`resultsEntered`) and how many of those are still to verify (`resultsToVerify`), counted on the standing sample.
- **Not here:** the report screen and the doctor's view of results (#92), outsourced tests (#94), a sample of several orders, analyser interfaces, and charging (billing reacts to `order.placed` and `order.completed`).
