# Patients API

What was decided for this feature's API. Moved out of `apps/api/CLAUDE.md` (#370); Claude Code loads it when a file of this folder is read. The web side's notes are in `apps/web/src/features/patients/CLAUDE.md`.

- **`features/patients`** is the first feature with patient data and the pattern for the next: `permissions.ts`, `schemas.ts` (TypeBox), `repository.ts` (SQL on `request.txClient`) and `routes.ts`. It is behind the `patients` module flag.
- **The MRN is assigned by the server** from `patient_mrn_counters`, one row per hospital, incremented in the registering request's own transaction: no gaps after a failure, no duplicates under concurrency. It is the hospital's initials and a seven-digit number (`SH-0000123`, so MRNs sort as text up to ten million per hospital) and never changes; a trigger refuses a change of hospital, MRN or registration details, and the app role has no DELETE on `patients`.
- **Search is `POST /patients/search`** with the term in the body, because it can be a name, a phone number or an MRN and must never be in a URL. Every word must appear in the name or MRN, in any order. `total` comes with the first page only.
- **The list is ordered and paged on plain stored columns** (`last_name_lower`, `first_name_lower`, `id`), and the cursor row's values are passed as parameters, so a deep page starts at the cursor through the index. The cursor holds the last row's id and the sort, no data; if that row is renamed between two pages, the next page starts from its new position.
- **`patient.contact:read` is a field-level permission.** Without it the phone is masked to its last four digits, email and address are left out, and contact details cannot be changed. Check it through `request.access.policy()`, since it is not one of the route's required permissions.
- **Searching by phone number needs `patient.contact:read` too.** Without it the term is matched against names and MRNs only: otherwise a masked number could be recovered digit by digit from which rows match.
- **Changing a record needs `patient:read` as well as `patient:update`,** because the answer is the whole record, and the narrower of the two scopes applies.
- **The duplicate check is a deliberate exception to scope and to the contact permission:** anyone who may register sees possible duplicates across the whole hospital, matched by name and birth date or by phone. That is what stops a second record for the same person. The matches are masked, carry no id, and the check is audited and rate limited.
- **Scope:** `own` means the patients the user registered, until encounters say whose patient someone is; `department` matches nothing yet. Another module that answers about a patient checks it with `patientInScope` from `index.ts` (queue, triage), so the meaning stays here.
- **A record outside the caller's hospital or scope is a 404,** the same answer as one that does not exist.
- **`POST /patients` requires an Idempotency-Key** and keeps only the id for a replay, so a replay answers `{ id }` and the client reads the record (which needs `patient:read`).
- **A birth date is checked against today at the hospital,** in its timezone, not the server's.
- **A change that sends what the record already has writes nothing and emits nothing.**
- **Every record has a `version`,** counted by a database trigger on each update. `PATCH /patients/{id}` requires `expectedVersion`, the version the caller read, and answers 409 `conflict` without changing anything when the record has moved on. The row is locked while the two are compared, so of two changes made from the same version exactly one goes through. Use the same pattern for any record two people can edit at once.
- **Audit:** record reads and updates through `config.audit`; create, search and duplicate check through `request.audit`. Events carry the patient id, and `patient.updated` the names of the changed fields, never values.
- **Unknown body fields are dropped by validation, not refused,** so a client cannot set `mrn`, `tenantId` or `id`.
- **Merging two records (#194, `merge.ts`, migration 0077).** `POST /patients/{survivor}/merge` with `sourcePatientId`, a reason and both `expectedVersion`s (idempotency key required; `patient:merge`, admin only, scope `all`). Nothing is deleted and no clinical row is rewritten: the source gets `merged_into_id` (set once, a trigger refuses to change or clear it), keeps its MRN, leaves search and the duplicate check, and cannot be changed (409 `patient_merged`; `PatientRecord.mergedInto` says where to go). Every module that keeps rows for a patient registers what it moves with `app.patientMerge.register(name, handler)` (`core/patient-merge`); the handlers run in the request's transaction after the source is marked, so a merge is whole or not at all (a handler that throws undoes everything, tested). Only documents register one so far. The merge is recorded in `patient_merges` (append-only, counts by module, never values), audited (`patient` update for both, `patient_merge` create) and announced as `patient.merged` (ids only). `GET /patients/{id}/merges` lists what was merged into a record. `GET /patients/{id}/merge-preview?source=` (#603) returns the rows each module would move, read only: a module passes a third argument to `register`, a counter with the handler's signature that changes nothing; without one it is left out of the preview.
- **Clinical modules and a merge (#557, migration 0107).** Rows stay on the record they were written for. Reads that show a patient's history include the records merged into it (`patientFamily` in `core/patient-merge/family.ts`, `patient_id = any($n::uuid[])`): the encounter list (the timeline), a patient's released lab results, the pharmacy queue and vitals, the admissions list filtered by `patientId` (#843), and a patient's allergies (prescribing and the pharmacy warning read nothing on the server: the screens call `GET /patients/{id}/allergies`, which, asked for a merged-away id such as an old prescription's, answers for its survivor through `survivorOf` (#865), so later allergies are not missed; `GET /patients/{id}/allergies` appends the items of the lists on merged-in records, version and status kept the survivor's; saving adopts them). Appointments, queue tokens, radiology, billing and nursing have no read keyed by a patient id (their lists are by day, status, admission or encounter, and each row keeps its own patient), so there was nothing to change; a future `patientId` filter on one of them must use `patientFamily`. Route-level 409 `patient_merged` tests for queue, allergies, admissions and appointments are in `merge-modules.test.ts`. Writes: a `BEFORE INSERT` trigger `refuse_merged_patient` on every table with `tenant_id` and `patient_id` (except `patient_merges`, `patient_documents`, `document_legal_holds`) raises SQLSTATE `PM409`, which the error handler answers as 409 `patient_merged`; a test fails for a new table with `patient_id` and no trigger (add the trigger in its migration). Updates to existing rows are not refused. Unmerge: see below.
- **The old registration number (#694, migration 0094).** `legacy_id`, optional text up to 50 characters (`PLAIN_TEXT`, tidied), unique per hospital where set (a partial unique index starting with `tenant_id`). On `POST /patients`, `PATCH` (null clears it), the `patients` import column `legacyId` and both read shapes. `POST /patients/search` also matches a term equal to it, exactly and case-sensitively, on the plain column (an `or` beside the word match, never a text scan). A number already in use is 409 `legacy_id_taken`; in an import it is reported on its own field (`legacy_id_taken`, and `duplicate_in_file` through `Prepared.unique`). Events and the audit log carry the field name only, never the number. It is not contact data, so `patient.contact:read` does not gate it. Sample import file with the column: `docs/samples/patients.csv` (#759); `legacyId` is optional per row.
- **Unmerging (#555, migration 0112).** `POST /patients/{source}/unmerge` (the record merged away; `patient:unmerge`, admin by default, idempotency key, reason) inside a window: `patient_settings.unmerge_window_days`, 30 by default, 0 turns it off, set with `PUT /patient-settings` (same permission), counted from `patient_merges.merged_at`. In one transaction the merge row is marked `unmerged_at/by/reason` (the only columns that may change, once), then `merged_into_id` is cleared: the `patients` trigger allows that only when the merge row was marked in the same transaction, and the documents trigger likewise lets rows go back only to `original_patient_id`. Modules reverse their moves through the 4th argument of `app.patientMerge.register` (an undo handler); a merge whose `moved` names a module with no undo gets 409 `unmerge_unsupported`. Documents are returned to the source; the whole-record legal hold the merge copied to the survivor is released in the name of the person who unmerged (#866): copies carry `merged_from_patient_id` (migration 0113), a hold placed by hand does not and stays, and each release is an audit entry (`document_legal_hold`, detail `unmerge:<merge id>`, whose row holds the reason); holds copied before 0113 have no marker and stay. Clinical rows never moved, so nothing else is reversed. Refused: not merged (`not_merged`), survivor merged away since (`patient_merged`), window over (`unmerge_window_closed`). A record may be merged again afterwards (the "merged away once" rule covers live merges only). Announced as `patient.unmerged`. No screen yet.

- **Search at very large hospitals (#259 spike, built in #864, migration 0114).** Built as decided below: `patient_search_ids(words, phone, legacy, merged_away)` and `patient_search_count`, owned by the no-login `mediflow_search` role (BYPASSRLS, select on six columns only), filter `tenant_id = app_tenant_id()` themselves, return ids; `searchPatients` puts them in `id in (select ...)` so the rows, the scope and the merged-away filter are applied again under row-level security, and the total counts the same way. The function builds one `like` per word with dynamic SQL. Rechecked at 300,000 rows on a 2-core machine: two common words 21 to 25 ms, a rare fragment 26 ms. The spike notes follow. Under row-level security Postgres uses an index for a clause only when its operator is leakproof, and `LIKE` is not, so the app role never uses the `gist (tenant_id, search_text gist_trgm_ops)` index: search reads every row of the hospital. Measured in a scratch database (Postgres 17, 2 cores, one hospital holding 90% of the rows): a two-word term took 0.43 s at 500,000 patients and 1.0 s at 2,000,000, a rare fragment 0.36 s, an MRN or phone fragment about 0.5 s; it grows linearly. Rejected: a prefix range on the name (leakproof, but 0.75 s because the planner walks the name index, and it cannot find the middle of a name); the gist index through a definer function (works, but 0.9 s for a rare fragment, the slowest index kind). **Decision:** search goes through a `SECURITY DEFINER` SQL function owned by a no-login role with `BYPASSRLS` and a fixed `search_path`, which filters `tenant_id = app_tenant_id()` itself (the tenant still comes only from the session setting) and returns ids, which the caller reads again under row-level security so a mistake in the function cannot show another hospital's row. It is backed by `gin (tenant_id, search_text gin_trgm_ops)` and the same on `phone_digits` (`btree_gin`), replacing the two gist indexes. Through that path: at 500,000 patients 51 to 65 ms for two common words, 4 ms rare fragment, 80 ms MRN fragment, 17 ms phone fragment; at 2,000,000 patients 43 to 76 ms, 11 ms, 69 ms, 16 ms. Write one `like` per word, not `like all (array)`, or the index is not used; sort the matches in a `materialized` CTE, or the planner walks the name index and takes 1.5 s. A term under three characters has no trigram and still scans (0.3 s at 2,000,000). Costs: the GIN index is 144 MB at 2,000,000 rows (table 300 MB), and inserting 1,500,000 rows into a table that already has it took minutes, so build the index after a very large import. **Decision (#881): documented, not deferred.** Dropping and rebuilding the indexes would leave search scanning for a live hospital while the build runs, and a go-live load of a huge register is rare; so the import centre says, before a patients file is chosen, that a file of a million patients or more takes minutes and should be loaded outside working hours. Revisit (drop the two GIN indexes, load, `create index concurrently`) if a pilot actually plans such a load. An equality lookup on `mrn` already uses its btree index (under 1 ms). A dedicated search store is not needed below several million patients in one hospital.
- **Words under three characters (#879, migration 0116).** A word with fewer than three characters has no trigram, so it matches the start of the first or the last name (btree `text_pattern_ops` indexes on `first_name_lower` and `last_name_lower`, read inside `patient_search_ids`), not any part of the name or MRN; longer words keep matching anywhere. "ob" finds Obrien, not Roberts. Nothing is refused, so typing ahead works. **Measured at 2,000,000 rows (#893), and it misses 100 ms.** Postgres 17, 2 cores, one hospital with 1,800,000 patients and another with 200,000, 40 first and 30 last names (so a one-letter word matches a large share, harsher than real registers), run as `mediflow_app` with the real queries, warm, count then first page of 25: "a" 254,000 matches, 0.6 to 0.8 s count and 3 to 4 s page; "r" 448,000 matches, 0.9 s and 4 s; "ra" 196,000 matches, 0.4 s and 1.7 s; "sh" 93,000, 0.23 s and 0.85 s; "a r" 35,000, 0.25 s and 0.5 s; "ra su" 2,500, 0.15 s and 0.15 s; no match 2 ms. The time is not the lookup: the two prefix indexes find the ids quickly, but the page then sorts every match by name, so it grows with the number of matches, not with the index. A prefix index on the MRN would not help (an MRN fragment is not the slow case), so none was added. Load for the test: 2,000,000 rows took 2.5 minutes with the search indexes dropped, then 5 to 20 s for each index. A short word only becomes fast when it is selective or combined with another word. Follow-up proposed: for a short word, either walk the name index in sort order and stop after the page, or leave the total out.
- **The total uses `patient_search_count` (#880).** For a search term and a caller whose scope is `all`, the first page's total comes from the function, so the outer query does not build a hash join on a common word; narrower scopes (and no term) keep the outer `count(*)`. Not re-measured at 2,000,000 rows (the count of a one-letter word took 0.6 to 1 s there, #893).
