# Queue API

What was decided for this feature's API (#79). Claude Code loads it when a file of this folder is read. The web side's notes, which hold the rules the screens and this API share, are in `apps/web/src/features/queue/CLAUDE.md`.

- **`features/queue`** is today's OPD tokens at the hospital, issued at the desk and called by doctors. Behind the `queue` module flag, with `queue:read` (admin, doctor, nurse, receptionist), `queue:create` (admin, receptionist) and `queue:call` (admin, doctor, nurse). It implements what `planned.openapi.json` held for the web app (#76), with the same names and codes.
- **One sequence per department per calendar day at the hospital,** not per doctor (the issue said per doctor; #76 decided per department, as a token may be for any doctor of it). "Today" is worked out in SQL from the hospital's timezone; no request names a day. A number comes from `queue_counters`, one row per department and day, incremented by `INSERT … ON CONFLICT DO UPDATE` in the same statement that inserts the token: the row lock makes a second desk wait and take the next number, and a refused token rolls its number back. `queue_tokens_number_taken` is the backstop.
- **The database holds the rules:** a partial unique index refuses a second token not yet served for a patient, department and day (`queue_tokens_one_open`, read as 409 `already_queued`); another lets a doctor serve one token at a time (`queue_tokens_one_called`); the guard trigger allows only `waiting -> called -> served`, `called -> skipped`, `skipped -> waiting`, makes `served` final, gives a token its doctor once (from none), never changes its number, day, department or patient, and counts `version`. No DELETE for the app role.
- **Call-next** takes a transaction-scoped advisory lock for the doctor, so one doctor's calls run one after another, then picks the first waiting token of the doctor's queue in call order `FOR UPDATE SKIP LOCKED`, so two doctors of a department calling at once never get the same patient. The token being served becomes `served` only once someone is called: `queue_empty` changes nothing. Call order is `(priority is null), issued_at, number`; the called and served lists are by `called_at`. A waiting token locked at that moment by a change of its priority is passed over for the next one: accepted, as the two would otherwise wait on each other.
- **A skipped token keeps its doctor,** so after "Back in the queue" it waits in the queue of the doctor who called it, not the department's. Its place there is its priority and its time issued.
- **Scope:** `all`; `department`, the tokens of the department of the caller's active doctor profile; `own`, the caller's own queue (given to their profile, or to nobody in their department). Someone with no profile sees nothing under either. `queue:create` with a narrower scope issues only in the caller's department (422 `unknown_department` otherwise); `queue:call` calls only doctors and changes only tokens it reaches (422 `unknown_doctor`, 404 `token_not_found`). The defaults are all `all`.
- **Issuing needs `patient:read` too,** checked in the handler from the policy and within its scope (`patientInScope` from `features/patients`), with the same 422 `unknown_patient` as an id that does not exist. An archived department is 422 `unknown_department`. A repeated request answers only within the scope the caller holds now.
- **Idempotency keys are required** on issuing, call-next and every change, and nothing of an answer is kept (`body: 'none'`), because each names a patient. Issuing and call-next set `request.idempotentId`, so a repeat answers with that token as it is now; a repeated change does nothing and answers likewise. Either is audited as a `read`.
- **A change is only of today's token:** one of another day is 404, as the board never shows it.
- **Audit:** `queue_token` with the token's id: `create` when issued, `update` for every change (call-next audits the token it serves and the one it calls), `read` for every row of a page. **Events** carry ids and codes only: `queue.token_issued` (token, patient, department, doctor or null, number, day) and `queue.called` (token, patient, department, doctor, call count, and the token served by the same call). M7 opens the OPD encounter from `queue.called`.
- **The board's stream** (`GET /queue/events`, through `core/live`): each change publishes `{ departmentId }` on the `queue` topic in its transaction, and the stream sends it as a `queue` event to the hospital's boards whose scope reaches that department. The checks the stream repeats, and when it ends, are in `apps/api/CLAUDE.md` (Live updates).
- **Exports** from `index.ts`: `tokenOfPatientToday`, which triage takes a reading for a token with, so what "today" means stays here.
- **Cursors carry the sort time in UTC to the microsecond** (`to_char`), whatever the session's `DateStyle`.
- **Seed:** `db:seed` issues five tokens of today in General Medicine at each sample hospital (two for its first doctor, one with a priority), once a day.
