# Operation theatre API

What was decided for this feature's API (BE-27, #180). Claude Code loads it when a file of this folder is read. The web calendar (OT-01, #176) is built against it; the checklist, anaesthesia record, operation note and procedure charges (OT-02 to OT-04) are not here.

- **`features/theatre`** keeps `ot_rooms`, `ot_bookings` and `ot_consumables` (migration 0086) behind the `theatre` flag. A patient needs the `patients` flag (422 `unknown_patient`), recording consumables the `inventory` flag (403 `feature_disabled`). Permissions: `theatre:read` and `surgery:schedule` / `surgery:perform` (admin, doctor, nurse), `theatre:manage` (theatres, admin).
- **No overlap, by the database:** three exclusion constraints on `tstzrange(starts_at, ends_at)` (half-open) for bookings that are `scheduled` or `in_progress`: the theatre (409 `room_taken`), the surgeon (409 `surgeon_busy`) and the patient (409 `patient_busy`). Cancelled and completed bookings free the time. Before writing, the request takes transaction advisory locks on the three ids in sorted order (`holdResources`): without them two simultaneous inserts that conflict on different constraints can end in a Postgres deadlock error (500) instead of the clean refusal. The surgeon is a doctor profile id (`practisingDoctor`), the procedure an optional `procedure` service (`orderableService`, category procedure); a span is at most 24 hours and may not be over already.
- **State** (guard trigger, final states are closed): `scheduled -> in_progress -> completed`, or `scheduled -> cancelled`. Only a scheduled booking is moved (`reschedule`: time, theatre, surgeon). Every change sends the `version` read (409 `version_conflict`); a wrong status is 409 `invalid_transition`.
- **Consumables** (`POST .../consumables`, while the surgery is in progress or completed) take units out of named batches at a stock place through `stockOut` of inventory in the same transaction, ledger source `theatre`, reason `theatre_use` (added to the ledger's checks and the contract's enums), source id the recording's `use_id`. Lock order: the booking, then inventory's. `ot_consumables` rows are append-only and keep the ledger entry of each batch; `stock.low` comes from inventory. A repeat with the same key takes nothing out again. No price or charge is posted here.
- **The calendar:** `GET /theatre/surgeries?from&to` (at most 62 days, cursor on start and id) lists what overlaps the range, cancelled ones only with `status=cancelled`. Rows carry ids only (patient id, no name): the web names the patient through `usePatientName`. Every surgery listed is audited as a read.
- **Events** (ids only, never the procedure, notes or reason): `surgery.scheduled` (also on reschedule, `rescheduled: true`), `surgery.started`, `surgery.completed` (patient, surgeon, theatre and the procedure service, for billing to charge), `surgery.cancelled`.
- **Decided: `theatre:read` implies seeing the surgery schedule** (patient id, procedure and notes) whatever the caller's `patient:read` scope, as `admission:read` and `queue:read` do; grant it with that in mind. Booking does check `patient:read` within its scope.
- **Idempotency keys are required** on every POST and nothing of an answer is kept (`body: 'none'`); a repeat answers from the record as it is.
- **Not here (proposed follow-ups):** linking a surgery to the inpatient admission, turnover time between cases, the checklist and anaesthesia (see #872 below), an `own` scope for surgeons, recurring theatre lists.
- **Peri-operative record (#872, migration 0115, `periop.ts`):** `ot_fitness` (one row per surgery, replaced by a new assessment, each audited), `ot_checklist_steps` (insert-only, one row per step: the server takes the time and the signed-in user, a repeat answers with the first entry) and `ot_anaesthesia` (a draft replaced until signed once, then closed by a trigger). `GET .../periop` needs `theatre:read` and is audited as a read; the writes need `surgery:perform` and a scheduled or in-progress surgery (409 `invalid_state`). Checklist phases are in order (pre-op, sign in, time out, sign out; 409 `phase_incomplete`), `surgery.checklist_step_completed` carries the patient id and the step, never the note. Every answer is the whole record. Not here: blocking surgery start on the checklist, an anaesthetist permission, a surgical team.

- **Operation note, visit and charges (#178, migration 0117, `operation.ts`):** `ot_bookings.encounter_id` (nullable) names the visit a surgery is charged to; `PUT .../encounter` (`surgery:schedule`) sets it to an **open encounter of the same patient** (422 `unknown_encounter`) while the surgery is scheduled or in progress (409 `invalid_state`), and the booking guard allows only that column besides the ones it already allowed. It bumps `version`. `ot_notes` is the operation note (one row per surgery): a draft replaced by `PUT .../operation-note` once the surgery is in progress or completed, signed once by `POST .../operation-note/sign` (then closed by a trigger; 409 `already_signed`), corrected by insert-only `ot_note_addenda` (`POST .../operation-note/addenda`, 409 `not_signed` before the signature). Reads need `theatre:read` and are audited as a read of the surgery; writes `surgery:perform`. Note text is never in an event or an audit entry.
- **Charges (billing's `posting.ts` listens):** `surgery.completed` now carries `encounterId` when linked, and billing posts the procedure service (`serviceId`) once as source `procedure`, `source_ref` `surgery:<id>`, priced from the list as for any service. The new event `surgery.consumables_used` (ids only: patient, `useId`, encounter) makes billing post one charge per batch taken at the batch's MRP, source `dispense`, `source_ref` `theatre:<consumable row id>` (flagged `no_price` without an MRP). **A surgery with no visit posts nothing**; linking a visit (`PUT ./encounter`) re-emits `surgery.consumables_used` for each earlier recording, so stock recorded before the link is charged then (#891), once, as the charges are keyed on the consumable row. A package covering the service voids the charge as usual. The consumables list now also answers `itemName`, `batchNumber` and `locationName`.
- **Returns (#892, migration 0119):** `POST /theatre/surgeries/{id}/consumables/{consumableId}/return` (`surgery:perform`, idempotent) puts units back into the same batch and place through inventory `stockIn` (source `theatre`, reason `theatre_return`), never more than used less returned (409 `over_return`), into insert-only `ot_consumable_returns` (reason, person, ledger entry). Consumables answer `returnedQuantity`. Event `surgery.consumables_returned` (ids only): billing voids the `theatre:<id>` charge when it is pending, on no invoice and wholly returned, and otherwise flags it `return_review` for the desk to credit (as for a dispense return); an invoiced charge is never changed.
- Not here: implant serial numbers and a count sheet, a screen for returns.
