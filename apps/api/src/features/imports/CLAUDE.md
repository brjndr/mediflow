# Import centre API

What was decided for this feature's API. Moved out of `apps/api/CLAUDE.md` (#370); Claude Code loads it when a file of this folder is read. The web side's notes are in `apps/web/src/features/imports/CLAUDE.md`.

- **`features/imports`** loads records of a kind from a file: rows staged by the web app, checked by a job, written by another. Behind the `imports` module flag, with `import:read` (the batches and their reports) and `import:run` (everything else), both the admin's by default. The web app's notes are `apps/web/src/features/imports/CLAUDE.md`.
- **The kinds are registered by the features that own them,** through `app.importKinds` (`core/imports/registry.ts`, registered before the features): `services`, `drugs`, `lab_tests` and `patients` today. A kind gives its module flag, the permissions loading it needs besides `import:run`, its columns (field and type), the schema a row is validated against (its create body, or a variant of it), and `prepare` and `write`. Loading a kind needs what adding one of its records on its own screen needs; patients need `patient:import` as well (`features/patients`).
- **A create route and its import share one path:** `prepare` checks and tidies (reads only, throws `HttpError` for the row, or `RowProblem` naming the field), and `write` inserts, audits and emits. Both take a `Writer`, which a request is and the import job's `JobWriter` imitates. A feature's `create.ts` holds them, and its route calls them. Change a create rule there, never in the route alone.
- **A row is text, field by field** (`convert.ts`): trimmed, empty is no value, then made a value of its column's type (whole numbers, yes or no, one of a list whatever its capitals, YYYY-MM-DD, or an amount read as minor units on its digits in the hospital's currency, grouped by commas or not), then validated against the kind's schema with Ajv, which is the validator the routes use. What is wrong is a field and a code, never the value.
- **States:** `staging` (rows arrive, 1,000 a request, 20,000 a batch; a line sent again is kept as first sent), `checking`, `checked` (with `problem_count`), `queued`, `running`, then `committed`, `failed` (with `failure`) or `cancelled`. Every change is made with the batch locked, and the route sends the job after its commit (`request.afterCommit`).
- **The dry run reads only, in one transaction, and takes no lock:** it calls `prepare` for every row and finds the duplicates within the file by the key `prepare` gives. **The commit writes every row in one transaction:** `prepare` again (the catalog may have changed), then `write`; one refusal rolls everything back and the batch fails with its report (`rows_refused`). It checks first that the person who asked still may (`permission_withdrawn`). A unique index lets one batch be queued or running at a hospital (409 `import_running`).
- **Jobs run as the app role at the batch's hospital,** as a request does. A delivery takes a batch with a `claim_token`, which every later change of the job names, so a delivery that was taken over changes nothing; the commit also holds an advisory lock on the batch, so a slow delivery and the one that took over never write at once. The heartbeat is written with the progress every 500 rows, in a short transaction of its own so the screen sees it; one older than ten minutes is free to take. A connection is given back exactly once (`atHospital`). A failed job is reported to the queue as `job_failed` with its SQLSTATE, never as the error: pg-boss keeps it in its own table, and a database error's text can quote the row it refused (`safeJobError`, for every job).
- **A refused write ends the writing:** the database may have aborted the transaction, so it rolls back, and the rows are checked once more without writing for a whole report (`rows_refused`), never `write_failed` for what is a refusal.
- **Audit:** each record written is audited as its route audits it, with `request_id` `import:<batch id>` and the person who asked for the commit as the actor; the batch itself has `create`, `stage`, `check`, `commit` and `cancel` on `import_batch`. Events are the records' own (`master.changed`, `patient.registered`).
- **Rows are deleted** when the batch is written, fails or is given up. `imports.expire` (hourly, as the worker role, which has a policy of its own on the two tables and a grant of only the columns it decides by) gives up what was left staged or checked for seven days (`expired`) and what stalled, waiting, checking or writing with no heartbeat for an hour (`stalled`), so a stalled batch does not keep its rows or block the hospital's next one.
- **A patient batch holds the MRN counter** from its first row to its commit. `POST /patients` sets `lock_timeout` to three seconds and answers 503 `busy` with `Retry-After` when it is not given the counter, so the desk is told to try again instead of holding a pooled connection every hospital shares for as long as the batch takes. Patient files are for going live, not for a busy morning. A patient row is refused only on the name and date of birth of someone registered, and contact consent is not taken from a file (`features/patients`).
