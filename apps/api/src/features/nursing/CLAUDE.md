# Nursing and ward care API

What was decided for this feature's API (BE-24, #163). Claude Code loads it when a file of this folder is read. No web screens yet; they build against this contract. Read `features/admissions` too: every record here belongs to a stay.

- **`features/nursing`** keeps what the ward records about an admitted patient: vital signs, the medication administration chart (MAR), progress notes, a read of the stay's diet orders and requests for ward stock. Behind the `nursing` flag; the stay needs the `admissions` flag, the chart and diet the `clinical` flag and stock requests the `inventory` flag (403 `feature_disabled`, checked in the handler as admissions does for `wards`). It never writes `encounters`, orders, indents or the ledger except through other modules' `index.ts` (`stayInScope`, `medicationOrder`, `medicationOrdersOf`, `dietOrdersOf`, `orderDispensed`, `requestIndent`, triage's limits and ranges).
- **Permissions:** `nursingVitals:read|record`, `mar:read|record`, `progressNote:read|write`. Nurse and admin hold all of them; doctors read. A write route also asks for the matching read, since its answer shows the record. Diet uses `order:read` and a stock request `indent:create` and `indent:read`: nurses get no `order:create`.
- **Scope** is the admission's, through `stayInScope` with the scope of the route's own permission (`own`: the admitting doctor; `department`: theirs). A stay out of scope, of another hospital or missing is one 404 (`admission_not_found`; `note_not_found` for the note routes). The admission row is locked (`for update`) by every write, so a discharge and a ward record take turns. The app role has no UPDATE on the append-only tables, so never `for update` on them.
- **Writes need an open stay:** 409 `admission_not_open` for anything but `admitted`. A trigger (`nursing_open_stay`) holds the same for every insert whoever writes (23514), and a note is not edited after discharge either. Reads of a finished stay stay open.
- **Append-only in the database** (migration 0084): `ward_vitals`, `mar_entries`, `progress_note_versions` and `ward_stock_requests` give the app role INSERT and SELECT only, and a trigger refuses UPDATE, DELETE and TRUNCATE to the owner too. Tests clean up with `session_replication_role = replica`. Every row names its admission, encounter and patient together (a foreign key to `admissions (tenant_id, id, encounter_id, patient_id)`, added as `admissions_tenant_stay`, and to `encounters`).
- **Ward vitals are their own table**, not triage's `vitals` (triage readings belong to a queue token and a patient; these to a stay). Same limits (`VITAL_LIMITS`) and flags against the age band's ranges that day, from triage's exports. `observedAt` (not in the future) is when it was taken. A correction is a new reading with `correctsId` and a reason, at the corrected reading's time, once (unique index, 422 `already_corrected`).
- **MAR** (`POST /mar/entries`, `/mar/entries/{id}/correct`, `GET /admissions/{id}/mar` and `/mar/orders`): an entry is an administration against a medication order of the stay's encounter (composite foreign key to `orders_tenant_id_medication`), for a slot (`scheduledAt`), with outcome `given | withheld | refused | missed`. One entry per order and slot (partial unique index, 409 `slot_recorded`); changing it is a correction (new row, same order and slot, reason, once). A reason is required unless given (422 `reason_required`, and in a check constraint). A given dose defaults to the order's dose and route. Beyond the doses a day the frequency allows (`dosesPerDay`: `1-0-1` is 2, `BD`, `TDS`, `q6h`; as-needed or unreadable frequencies set no limit) a given dose needs a reason (422 `extra_dose_reason_required`); the count is a rolling 24 hours before the slot, entries that were corrected left out. A cancelled order is refused (409 `order_cancelled`); an order of another encounter 422 `unknown_order`. **It records the administration only:** it does not move the order's status and never calls the pharmacy. The answer carries `warnings: ['not_dispensed']` when nothing was dispensed (a warning, not a refusal; not repeated on a replay). `witnessId` is optional and must be another active member (422 `unknown_witness`); no rule requires one yet (high-risk medicines are a follow-up).
- **Progress notes** are the one editable table: only `body` moves (a trigger keeps the rest), `version` is checked on `PATCH` (409 `conflict`), only the author edits (403 `not_author`), and each text is kept in `progress_note_versions` (inserted in the same transaction, version 1 at creation). `GET /progress-notes/{id}/history` lists them newest first. Plain text of up to 4000 characters.
- **Diet:** `GET /admissions/{id}/diet` reads the diet orders from clinical; there is no table here.
- **Ward stock:** `POST /admissions/{id}/stock-requests` makes an indent from the ward's place (`fromLocationId`) to a store through inventory's `requestIndent` in the same transaction and links it in `ward_stock_requests`. Approval and issue are the indent routes', as for any indent.
- **Idempotency keys are required** on every POST; nothing of an answer is kept (`body: 'none'`), `request.idempotentId` is the new row's id and a repeat answers with the record as it is now (audited as a read, scope checked again).
- **Events** (ids, codes and the outcome or kind only, never text): `vitals.recorded` (`setting: 'ward'`, with the admission and `correctsId` for a correction), `medication.administered` (every entry including withheld ones, with `outcome`, `correctsId` for a correction; a consumer that charges must look at `outcome`), `progressnote.created` / `progressnote.updated`, `ward.stockrequested`. A rolled-back request emits nothing. **Audit entities:** `ward_vitals`, `mar_entry`, `progress_note`, `ward_stock_request` (and `stock_indent`, `order` for the reads of orders): create, update and a read for each row of a page.
- **Logging:** free text sits in `body`, `reason` and `note`, already redacted.
- **Not here (proposed follow-ups):** web screens and MSW mock; a witness rule for high-risk medicines; a MAR schedule generated from the frequency (due and overdue doses); intake and output, pain and other charts; handover reports; charging consumables used on the ward; a patient/bedside barcode check.
- **Review fixes:** a dose `scheduledAt` must be after the order was placed and at most 24 hours ahead (422 `slot_out_of_window`; a correction keeps the corrected slot). The orders list is capped at 100, not paged. Module flags (`clinical`, `inventory`) are checked before a replay too. The open-stay trigger is told apart from other CHECK violations by its message. **Gap:** a stock request `fromLocationId` may be any place in use other than the store asked (inventory indents do not require a ward or department kind), so a store can be named as the requesting place; tightening that belongs to inventory.

## Fluid balance and care plans (#160, NR-04; migration 0095)

- **Permissions:** `fluidBalance:read|record` and `carePlan:read|write`. Nurse and admin hold all; doctors read. A write route also asks for the matching read. Scope, stay lookup, the open-stay rule and idempotency are as above (the helpers are exported from `routes.ts`; the new routes are in `care-routes.ts`, SQL in `care-repository.ts`, schemas in `care-schemas.ts`).
- **`ward_fluids`** is append-only like vitals (trigger, INSERT and SELECT only for the app role). An entry has a direction and a kind (a check ties them), whole millilitres 1 to 5000 and `observedAt` (not in the future). A correction names the entry (`corrects_id`, a reason, once: 422 `already_corrected`), keeps the direction (422 `direction_changed`) and the corrected entry's time. **Totals** (`GET /admissions/{id}/fluids/totals?from&to`, from included, to excluded, at most 36 hours) count an entry that has been corrected as its correction; the server adds them, the web shows one request for each shift. The list takes the same `from` and `to`.
- **`care_plans`** and **`care_plan_tasks`**: a plan has a problem, an optional goal and a status that only moves from `active` to `completed` or `cancelled` (409 `plan_closed` afterwards, also for adding a task or doing one). A task's description is fixed; it is done once (409 `already_done`) by whoever marks it, with an optional note. Neither is deleted; triggers hold the rest (only status, only the doing) and the open stay. A plan is created with up to 20 tasks in one request; `POST /care-plans/{id}/tasks` adds one (idempotency key required, replays answer with the plan as it is). Done and close are plain POSTs and not repeatable by design (the second answer is the 409).
- **Events and audit:** `fluid.recorded` (id, direction, `correctsId`), `careplan.created`, `careplan.task_done`, `careplan.closed`: ids and codes only. Audit entities `ward_fluid` and `care_plan`. Totals are audited as one read of the stay's balance.
- **Not here:** targets or fluid restrictions, a balance carried between days, a task assigned to a nurse, due or overdue tasks on a worklist, charging consumables.
