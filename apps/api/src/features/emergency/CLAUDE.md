# Emergency API

What was decided for this feature's API (BE-26, #175). Claude Code loads it when a file of this folder is read. The web board (ER-01, #171) runs against it; care and disposition (ER-02, #172) are in the last section; medico-legal records (ER-03, #173) are in the last section.

- **`features/emergency`** keeps `er_encounters` (migration 0085), one row per arrival, behind the `emergency` flag; a patient on record needs the `patients` flag. Permissions `emergency:read` (admin, doctor, nurse, receptionist), `emergency:register` (admin, nurse, receptionist) and `emergency:triage` (admin, doctor, nurse).
- **Temporary identity:** `tempId` (ER-0042) is `temp_no` from a per-hospital counter row (`er_counters`, upserted in the registering transaction, so numbers do not repeat and a rolled-back registration gives its number up). It never changes. A case may name a patient at registration or stay unidentified with an optional alias, sex and approximate age.
- **Identify and undo:** `POST .../identify` links an unidentified case to a patient (once, 409 `already_identified`) and writes a row to `er_case_links` (who, when). `POST .../unidentify` undoes it within `UNLINK_WINDOW_HOURS` (24) with a reason: the link row is closed, never deleted (a trigger allows only that one change), the case is unidentified again and may be linked to the right patient. A case registered with a patient, or past the window, is 409 `not_reversible` / `window_closed`. This is the "merge" of the temporary identity into a record; merging two patient records stays the documents module's `POST /patients/{id}/merge`.
- **Triage:** category 1 to 5, set at registration or by `POST .../triage`; `er.triaged` carries the category and the previous one, never the complaint. Guard trigger: only the patient, category, status and their timestamps change; a disposed case is closed.
- **Board:** `GET /emergency/cases`, untriaged first (category 0), then category, then arrival; cursor carries those three values; `total` on the first page. Every case listed is audited as a read (the complaint is health information).
- **Idempotency:** all writes require an `Idempotency-Key` and store status only (`body: 'none'`); a repeat answers from the current record, doing no work. Edits send the case `version` (409 `version_conflict`).
- **Events:** `er.registered`, `er.triaged`, `er.identified`, `er.unidentified` (ids, codes and numbers only).
- **Care and disposition (ER-02, #172, migration 0087).** New permissions `emergency:care` (admin, doctor, nurse: start treatment, notes, open the encounter) and `emergency:dispose` (admin, doctor: decide how the patient leaves). Routes: `GET /emergency/cases/{id}`, `POST .../start` (waiting to in_treatment), `POST .../encounter`, `GET|POST .../notes`, `POST .../disposition`.
- **Rapid orders are the clinical module's orders.** `POST .../encounter` opens an `er` encounter (`openEmergencyEncounter`, clinical; needs `encounter:create` too, so a nurse cannot; needs the patient on record, 409 `identify_first`, and the clinical flag) and the web app places lab, imaging and procedure orders on it through `POST /encounters/{id}/orders` (so `order:create`: doctor and admin). The case keeps `encounterId`. Nothing here writes `orders`. Once open, the case cannot be unlinked (409 `has_encounter`), and the clinical close and cancel routes refuse an `er` encounter (409 `managed_by_emergency`): only the disposition closes it (409 `unsigned_notes` while a note is a draft).
- **Notes** (`er_notes`, observation or assessment, plain lines up to 2000) are append-only (insert and read grants only; a correction is a new note) and may be written for an unidentified patient: they belong to the case, not to the encounter. Read and write need `emergency:care`; reads are audited per note.
- **Disposition** is once and final (the guard trigger): `discharge`, `admit`, `refer` (destination required) or `expired` (time of death required, not in the future). A CHECK ties `status = 'disposed'` to a disposition. `admit` calls `admitFromEmergency` (admissions): the patient must be on record, the admissions flag on and `admission:create` held (403 otherwise); it opens the admission of type `emergency` with its `ipd` encounter, without a bed (assign one on the bed board), in the same transaction, and keeps `admission_id` on the case. History is preserved by linking, not copying: the `er` encounter, its orders and notes stay as they were and the patient's timeline shows both visits. The note on an admit is the admission's advice note. Events `er.started`, `er.disposed` (type and ids only) and, for admit, `encounter.opened` and `admission.created`.
- **Not here (proposed follow-ups):** marking the patient deceased on the patient record when expired (only the case records it), bed choice at admission, emergency charges, a hospital's own waiting targets, a push stream for the board, a web screen to undo a link.
- **Medico-legal (ER-03, #173, migration 0088).** `PUT|GET /emergency/cases/{id}/medico-legal`. A case is flagged by recording `er_medico_legal` (category, account of the injury, brought by, police informed with station and reference); every save is a new row (`revision`, insert and read grants only), the highest is current, and a save carries the revision read (0 to flag; 409 `version_conflict`). The case carries `medicoLegal` (a computed boolean, visible to `emergency:read`); the details need `medicoLegal:read`, flagging and revising `medicoLegal:manage` (both admin and doctor by default; a nurse can see the flag only). Every view of the details is audited as a read, also a repeat; saves are audited and emit `er.medico_legal` (case id and revision only, never the narrative). Allowed after disposition. The register: `GET /emergency/cases?medicoLegal=true` (#676), flagged cases only, any status unless one is given, newest arrival first (cursor on arrival and id), `emergency:read` like the board, since the flag is visible to it; it carries no details. Not here: an access reason.
- **Printing the medico-legal record (ER-03a, #646).** `POST /emergency/cases/{id}/medico-legal/print` (`medicoLegal:read`, `Idempotency-Key` required) answers the latest revision and audits it as action `print`, entity `er_medico_legal`, entity id the case and detail `revision:<n>` (`audit_log.detail`, #675: a short code, never a field value), once per key. The web app draws the page from that answer, so the revision printed is the one recorded; it does not read the record again (which would audit a view as well).
