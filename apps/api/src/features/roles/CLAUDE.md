# Roles API

What was decided for role management (BE-16, #137). The role list (#133) and the permission matrix (#134) are built: `apps/web/src/features/roles/CLAUDE.md`.

- **`features/roles`** has no module flag (like staff). Permissions `role:read` and `role:manage`, defaults to `admin` only. Routes: `GET /roles`, `GET /roles/{roleId}`, `GET /permission-catalog` (every registered permission with its description, module and `scopes` it can be held at, for the editor; `scopes` starts with `all` and has the narrower ones only for a permission whose definition lists them, today the appointment ones; it is not under `/roles/` because a role id may be any slug), `POST /roles`, `PUT /roles/{roleId}` (rename and/or replace the whole set of grants), `DELETE /roles/{roleId}`.
- **Migration 0076** gives the app role narrow write grants: INSERT of `(tenant_id, id, name)` (so a new role is never built-in), UPDATE of `roles(name, updated_at)` and `role_permissions(scope)`, DELETE. A trigger refuses, for the app role only, renaming, re-identifying or deleting a built-in role, as a backstop behind the API. Migrations, the platform role and the cascade from a deleted hospital are not held back.
- **Built-in roles keep their identity:** same id and name always (409 `built_in_role` on a rename or delete); their permissions can be changed. A default an admin removed is not put back (`role_default_grants`).
- **Custom roles:** the id is made from the name (`roleIdFrom`), 409 `role_exists` when the id or the name (any case) is taken. Deleting needs no member (any status) and no invitation naming it (409 `role_in_use`).
- **Nobody hands on more than they hold:** creating, and editing both the grants a role has now and the ones it is to have, go through `grantsWithin` against the caller's policy (403 `role_not_allowed`). So a role above the caller cannot be edited or deleted by them.
- **The hospital keeps people who can manage it:** every change takes a per-hospital advisory lock, then locks the active members holding `role:manage` or `staff:manage` in user-id order (the order staff deactivation uses), and afterwards checks that someone still holds each (409 `last_admin`) and that the caller's own role still holds `role:manage` if it was the one edited (409 `cannot_remove_own_access`, checked first). Not covered: deactivating the last `role:manage` holder through `staff:manage`, and moving a member to another role (no API yet) must check the same.
- **Policy refresh:** triggers from migration 0006 move `tenants.policy_revision` on any role or grant change, and the policy is read per request, so the change applies on the next request and to the next `GET /session/policy`. Audited as `create`/`update`/`delete` on entity `role` (ids only).
- **Not done:** a per-role authenticator requirement (issue comment from #251; `mfaStanding` would read a flag on the role).
- **No version on `PUT /roles/{roleId}`:** two administrators saving at once is last write wins; the web matrix reads the role again before saving and merges (see its notes). An `expectedVersion` is a possible follow-up.
