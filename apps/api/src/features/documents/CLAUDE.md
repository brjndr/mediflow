# Documents API

What was decided for this feature's API (BE-29, #194). Claude Code loads it when a file of this folder is read. The merge of two patient records is in `features/patients/merge.ts` (see that folder's `CLAUDE.md`). No web screen yet (MR-01 to MR-04, #189 to #192).

- **`features/documents`** keeps files on a patient's record (`patient_documents`, migration 0077), behind the `documents` module flag. Categories: `consent`, `referral_letter`, `outside_report`, `id_proof`, `insurance`, `certificate`, `other`. Types: JPEG, PNG and PDF, at most 25 MB. An optional `encounterId` must be an encounter of the same patient (422 `encounter_mismatch`); the table only holds a foreign key to the encounter, so a merge can move a document without breaking it.
- **Permissions:** `document:read` and `document:upload` (admin, doctor, nurse, receptionist), `document:retire`, `documentRetention:read` and `documentRetention:manage` (admin). Every route reaches a document through the patient's scope for the permission (`patientInScope`), so another hospital's, or an out-of-scope, id is the same 404.
- **The upload is radiology's (#99), copied:** `POST /patients/{id}/documents` (idempotency key required, nothing of the answer kept) inserts a `pending` row and gives a signed `uploadUrl`; the public `PUT /document-uploads/{id}` checks type, exact size and the first bytes, stores the file at `documents/<tenant>/<id>` and sets `scanning`; the job `documents.scan` (the `app.scanner` interface) sets `clean`, or `infected` / `failed` and deletes the file; `GET /documents/{id}/download-url` (audited `export`) gives a signed link for a `clean` file served by the public `GET /document-files/{id}`. Links are signed for their own purposes (`signDocumentUpload`, `signDocumentDownload`). `asWorker` and `looksLike` moved to `core/files/worker.ts` for this feature; radiology still has its own copies (a follow-up to share them). The built-in scanner finds only the EICAR test string until a real engine is connected.
- **Nothing deletes a document.** The app role can only SELECT, INSERT and UPDATE a few columns: a document is retired (`POST /documents/{id}/retire`, a reason, at the version read; once only, a trigger refuses a second) and is then left out of the list unless `includeRetired`. A retired document can still be downloaded. The version counts retirements and merge moves, not the scan.
- **Retention.** `document_retention_rules` holds the years per category (`PUT /document-retention/{category}`, `null` removes the rule: kept for ever, the default). `retain_until` is worked out when the upload is asked for, at the hospital's date, so a later rule never shortens or lengthens a document already kept. The job `documents.sweep` (daily 03:30 UTC, worker role, across hospitals) deletes the file of each `clean` document past `retain_until`, files first, then marks the row `purged` and drops `file_key`; the row stays as the record that it existed. A file that cannot be deleted keeps its row and is tried the next day (a warning with a count is logged). Each purge writes an `audit_log` entry (`purge`, `patient_document`, no actor) into the owning hospital’s log, in the same transaction as the row (the worker role may only INSERT into the log, migration 0082); the daily count is also logged.
- **Legal hold** (#559, migration 0082, `document_legal_holds`): `POST /documents/{id}/legal-hold` or `POST /patients/{id}/legal-hold` (every document of the patient, later ones too), `GET /legal-holds` (active, cursor), `POST /legal-holds/{id}/release`. Needs `documentRetention:manage` (read: `documentRetention:read`); holds are never deleted, placing and releasing are audited. The sweep skips a held document, taking the row lock then reading the holds; placing a hold locks the same rows first, so none slips through. A merge copies the source's active patient holds to the survivor in the merge transaction (#629), so moved documents stay covered; holds on one document follow it by document id, and the source's own hold stays as it was.
- **A merge moves documents** through `app.patientMerge` (`core/patient-merge`): the handler runs whether or not the hospital has the `documents` switch on. The database lets a document change patient only to the record its old patient was merged into (trigger), and keeps `original_patient_id`.
- **Not here:** consents and certificates as their own records (MR-02), a sweep of uploads asked for and never sent, a presigned-URL S3 store (the `FileStore` is still a local folder), and DICOM.

- **`consents` and `records` permissions (#671)** are declared in `records-permissions.ts` and registered by this plugin under the module ids `consents` and `records`, so the platform's module list offers their switches. Both modules are web-only (mock) until their own APIs exist; those APIs should take the permissions over into their own feature folders.
