# Documents API

What was decided for this feature's API (BE-29, #194). Claude Code loads it when a file of this folder is read. The merge of two patient records is in `features/patients/merge.ts` (see that folder's `CLAUDE.md`). No web screen yet (MR-01 to MR-04, #189 to #192).

- **`features/documents`** keeps files on a patient's record (`patient_documents`, migration 0077), behind the `documents` module flag. Categories: `consent`, `referral_letter`, `outside_report`, `id_proof`, `insurance`, `certificate`, `other`. Types: JPEG, PNG and PDF, at most 25 MB. An optional `encounterId` must be an encounter of the same patient (422 `encounter_mismatch`); the table only holds a foreign key to the encounter, so a merge can move a document without breaking it.
- **Permissions:** `document:read` and `document:upload` (admin, doctor, nurse, receptionist), `document:retire`, `documentRetention:read` and `documentRetention:manage` (admin). Every route reaches a document through the patient's scope for the permission (`patientInScope`), so another hospital's, or an out-of-scope, id is the same 404.
- **The upload is radiology's (#99), copied:** `POST /patients/{id}/documents` (idempotency key required, nothing of the answer kept) inserts a `pending` row and gives a signed `uploadUrl`; the public `PUT /document-uploads/{id}` checks type, exact size and the first bytes, stores the file at `documents/<tenant>/<id>` and sets `scanning`; the job `documents.scan` (the `app.scanner` interface) sets `clean`, or `infected` / `failed` and deletes the file; `GET /documents/{id}/download-url` (audited `export`) gives a signed link for a `clean` file served by the public `GET /document-files/{id}`. Links are signed for their own purposes (`signDocumentUpload`, `signDocumentDownload`). `asWorker` and `looksLike` moved to `core/files/worker.ts` for this feature; radiology still has its own copies (a follow-up to share them). The scanner is `MALWARE_SCANNER`: `test` (EICAR only, development) or `clamav` (#560, `core/files/clamav.ts`, clamd over TCP with INSTREAM; a daemon error throws so the job retries and the file stays held).
- **Unsent uploads (#560, migration 0116):** `documents.unsent` runs hourly and marks a `pending` row older than an hour `failed` with `scan_result = 'never_sent'` (the one case where a non-pending row has no `uploaded_at`). Radiology does the same with `radiology.unsent`.
- **Nothing deletes a document.** The app role can only SELECT, INSERT and UPDATE a few columns: a document is retired (`POST /documents/{id}/retire`, a reason, at the version read; once only, a trigger refuses a second) and is then left out of the list unless `includeRetired`. A retired document can still be downloaded. The version counts retirements and merge moves, not the scan.
- **Retention.** `document_retention_rules` holds the years per category (`PUT /document-retention/{category}`, `null` removes the rule: kept for ever, the default). `retain_until` is worked out when the upload is asked for, at the hospital's date, so a later rule never shortens or lengthens a document already kept. The job `documents.sweep` (daily 03:30 UTC, worker role, across hospitals) deletes the file of each `clean` document past `retain_until`, files first, then marks the row `purged` and drops `file_key`; the row stays as the record that it existed. A file that cannot be deleted keeps its row and is tried the next day (a warning with a count is logged). Each purge writes an `audit_log` entry (`purge`, `patient_document`, no actor) into the owning hospital’s log, in the same transaction as the row (the worker role may only INSERT into the log, migration 0082); the daily count is also logged.
- **Legal hold** (#559, migration 0082, `document_legal_holds`): `POST /documents/{id}/legal-hold` or `POST /patients/{id}/legal-hold` (every document of the patient, later ones too), `GET /legal-holds` (active, cursor), `POST /legal-holds/{id}/release`. Needs `documentRetention:manage` (read: `documentRetention:read`); holds are never deleted, placing and releasing are audited. The sweep skips a held document, taking the row lock then reading the holds; placing a hold locks the same rows first, so none slips through. Every document in a list carries `held` (#672): an active hold on it or on its patient, worked out in `COLUMNS` with the same test as the sweep, so a hold of another hospital never shows (RLS). Placer and release history are not exposed. A merge copies the source's active patient holds to the survivor in the merge transaction (#629), so moved documents stay covered; holds on one document follow it by document id, and the source's own hold stays as it was.
- **A merge moves documents** through `app.patientMerge` (`core/patient-merge`): the handler runs whether or not the hospital has the `documents` switch on. The database lets a document change patient only to the record its old patient was merged into (trigger), and keeps `original_patient_id`.
- **Not here:** a presigned-URL S3 store (the `FileStore` is still a local folder), and DICOM.

- **`consents` and `records` permissions (#671)** are declared in `records-permissions.ts` and registered by this plugin under the module ids `consents` and `records`, so the platform's module list offers their switches. Both modules are web-only (mock) until their own APIs exist; those APIs should take the permissions over into their own feature folders.

- **Correction requests (#556, migration 0108, `corrections.ts`)** behind the `records` switch: `POST /patients/{id}/correction-requests` (an idempotency key, the target `patient`, an `encounter` or a `document` of that patient, `proposed` and `reason`), `GET` of a patient's requests and `GET /correction-requests` (the hospital's, `correction:read` with scope `all`), and `POST /correction-requests/{id}/approve|reject` (a reason, at the version read). A correction is never a silent edit: the request holds author and reason, approving edits nothing, and another module applies the change through its own amendment flow, reacting to `correction.approved` (`correction.requested` and `.rejected` too; ids and target kind only). The author cannot decide their own request (403 `second_person_required`, and a CHECK in the table), a request is decided once (409 `already_decided`, and a trigger). Permissions `correction:read` / `request` (admin, doctor, nurse, receptionist) and `decide` (admin). No web screen yet.

- **Blocked uploads are told to the uploader (#673, migration 0124):** when the scan job ends `infected` or `failed` it writes, as the worker role in one transaction, an `audit_log` entry (`scan_blocked`, `patient_document`, no actor, `detail` the scan result code, never the file) and a `document.blocked` event (actor = the uploader, payload `status`). `GET /documents/blocked` gives the caller's own blocked, undismissed, unretired documents (`created_by = caller`, at most 50, whatever the patient) and `POST /documents/{id}/dismiss-blocked` sets `blocked_seen_at` (404 for another person's or another hospital's; the version is not bumped). Needs `document:upload`. Unsent uploads closed by the hourly sweep (`never_sent`) appear in the list but write no event. The decision: only the uploader is notified.

- **Medical records desk (#570, migration 0132, `records-desk.ts`)** behind the `records` switch, registered by this plugin (no `app.ts` edit). `GET /records/incomplete`: closed encounters with their gaps worked out in SQL on every read, never stored: `unsigned_note` (a draft note), `no_diagnosis` (no unretracted diagnosis), `no_discharge_summary` (an `ipd` encounter whose admission has no signed summary, or a `daycare` or `er` encounter that an admission names as its source (`admissions.source_encounter_id`, #985) whose admission has none), `missing_consent` (a non-cancelled procedure order and neither a `consent` document, scanning or clean and not retired, nor a structured consent that names the encounter and is not withdrawn (#984, migration 0143, optional `encounterId` on `POST /patients/{id}/consents`, 422 `encounter_mismatch`)). Oldest first by `ended_at`, `total` on the first page. `POST /records/incomplete/{id}/assign` keeps a doctor in `record_assignments` (a note for the desk), `doctorId` null removes it, 422 `not_practising` otherwise. `GET /records/coding-queue` lists text diagnoses of closed encounters; a code is kept in `diagnosis_codings` because `encounter_diagnoses` is append-only. `version` is 1 while uncoded and one more per coding; a stale one is 409 `version_conflict`; only ICD-10 codes (422 `not_icd10`). `/record-requests` (list soonest due first, `overdue=true` keeps open ones due before today on the hospital clock and its `total` is the widget count (#988), create dated on the hospital's clock, `close` once with a note at the version; a trigger refuses any change to a closed row, 409 `already_closed`). Every desk route needs its permission with the scope `all`; `medicalRecord:assign` joins the four permissions (admin). Reads and writes are audited. **Events and a fee (#986, migration 0144):** `record.request_created` (patient, requester kind), `record.request_closed` (patient, outcome, and the fee when there is one) and `diagnosis.coded` (code id); ids and codes only. The names are `record.request_*`, not `record_request.*`, because the outbox allows letters only before the first dot. Closing a request as fulfilled may carry `feeServiceId`, `feeEncounterId` (a visit of the patient) and `copies`, kept on the request; billing listens to `record.request_closed` and posts one `service` charge to the visit (`source_ref` `record_request:<id>`, priced from the list, quantity = copies), so a repeat posts nothing. The records module never writes a charge. Not here: releasing the record itself, a screen for choosing the fee.

- **Consents and certificates (#566, migration 0134, `consents.ts`)** behind the `consents` switch, registered by this plugin (permissions in `records-permissions.ts`, plus `certificate:configure` for admins). `GET/POST /patients/{id}/consents`, `GET /consents/{id}`, `GET/POST /patients/{id}/certificates`, `GET /certificate-formats`, `PUT/DELETE /certificate-formats/{kind}`. Tables `patient_consents`, `patient_certificates`, `certificate_formats`, `certificate_counters`. The app role can only SELECT and INSERT the first two (no UPDATE, no DELETE grant): a mistake is a new record. A consent stores the filled text and the template id and version (a foreign key to `template_versions`; 422 `template_not_found` when it is not a consent template of the hospital, 422 `placeholders_unfilled` while a `{{x}}` is left); a drawn signature is SVG path data (`[ML0-9 .,-]`, a CHECK too), a typed one has none (422 `signature_invalid`). A certificate is checked against the hospital's fields for its kind (`certificate_formats`, or `STANDARD_FIELDS` in `certificate-fields.ts`, the same list as the web app's), keeps the `layout` it was issued under, and is numbered `MED|FIT|BIR|DTH-<year of issuedOn>-<4 digits>` from `certificate_counters` (an upsert that locks the row, so numbers are in order and never repeat). Reads are audited per row; both lists follow a patient merge through `patientFamily` (rows stay on the record they were written for, new ones for a merged record are refused, 409 `patient_merged`). Events `consent.signed` and `certificate.issued` (ids and kind). Idempotency key required on both POSTs. **Witnesses and withdrawal (#989, migration 0140):** `POST /consents/{id}/witnesses` adds a witness signature (name, relation, typed or drawn) and `POST /consents/{id}/withdraw` withdraws the consent once with a reason (409 `already_withdrawn`); both are new rows in `consent_witnesses` and `consent_withdrawals` (SELECT and INSERT only, the signed consent never changes), need `consent:sign` (witness) and `consent:withdraw` (withdrawal, granted separately, #1035, seeded for the same roles as sign), an idempotency key, and emit `consent.witnessed` and `consent.withdrawn`. A withdrawn consent takes no witness (409 `consent_withdrawn`). `Consent` carries `witnessCount` and `withdrawnAt`; the single read adds `witnesses` and `withdrawal`. Not here: a screen for either (the web mock only reads the new fields), a screen for naming the encounter. The rendered PDF is #990 (see below).

- **Rendered consents and certificates (#990, migration 0146, `pdf.ts`, `rendered.ts`)**: `POST /consents/{id}/document` (needs `consent:read` and `document:upload`) and `POST /certificates/{id}/document` (`certificate:read` and `document:upload`) render the record as a PDF on the server and keep it as a `patient_documents` row of category `consent` or `certificate` (the consent's encounter when it names one), stored `clean` with no scan because the server made the bytes (`scan_result` `generated`). The source is named on the row (`source_consent_id` / `source_certificate_id`, unique), so asking again returns the same document: it is a snapshot, a witness or withdrawal added later is not in it (a new rendering would need the old document retired first, not built). The PDF is written by our own small writer (`pdf.ts`, no dependency): A4, Helvetica, wrapped text, a drawn signature as strokes. Standard fonts hold Latin-1 only, so other scripts (Hindi names) print as `?` until a font is embedded. 409 `patient_merged` for a merged record. Not here: a button on the Consents tab, a PDF with the hospital's logo or letterhead.
- **Files stuck in scanning (#1063, migration 0151):** the job `documents.stuck_scan` (hourly at :45, worker role, across hospitals) sends the scan job again for a `scanning` document received more than `STUCK_SCAN_HOURS` (3) ago, with a job id `scan-<id>-<hour>` (the first id is spent once its retries ran out), and logs a `patient_documents_scan_stuck` warning with the count. The scan is idempotent, so a repeat is safe.
