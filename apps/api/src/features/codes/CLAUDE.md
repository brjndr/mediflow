# Diagnosis and procedure codes API

What was decided for this feature's API. Moved out of `apps/api/CLAUDE.md` (#370); Claude Code loads it when a file of this folder is read. The web side's notes are in `apps/web/src/features/codes/CLAUDE.md`.

- **`features/codes`** is the code sets a diagnosis or a procedure is recorded with, and each hospital's favourites among them. Behind the `codes` module flag, with `code:read` for everyone who records, reads or bills a diagnosis, and `code:manage` for the admin, who chooses the favourites.
- **The codes are shared by every hospital:** `codes` has no `tenant_id` and no row-level security, and the app role can only read it. It is the one table of hospital-facing data like that, because nothing in it is a hospital's own. Only `code_favourites` carries the tenant. A test (`test/tenancy.test.ts`) lists the tables a request reaches without row-level security, with what it may do to each: `codes`, read. Another shared table is added to that list on purpose, or the test fails.
- **A set is loaded by an operator, never by a request,** and none is in the repository: `pnpm --filter api codes:load --system=icd10 --file=<path>` (`load-cli.ts`), from comma-separated UTF-8 text whose first line is `code,title` (a file in another encoding is refused: it would load with every accent damaged). A relative path is from where the command is run. The whole file is checked before anything is written, in one transaction, and a refusal names the line and never a value. `--dry-run` says what a file would do and writes nothing: use it first, because a set loaded under the wrong `--system` cannot be taken out. In production it runs in the image (`node dist/features/codes/load-cli.js`) with the migrating login and the environment of the migrate step, and the file mounted into the container; a failure of the database is reported by its code only (42501 is a login that may not write codes). Loading a set again adds the codes it gained and changes the titles that changed. Nothing is ever removed: a diagnosis recorded with a code, and a favourite, still name it. `apps/api/sample-codes` holds a sample for development, which `db:seed` loads into a set only while that set is empty, so a real set loaded on a developer's machine keeps its titles (#316). Which edition the pilot hospital loads is #304.
- **A set holds a code once, however it is written:** `A09` and `a09`, or `E11.9` and `E119`, are one code (a unique index on the code without its dot and in lower case, migration 0027). The loader refuses a file that has both, or that writes a code the set holds another way, naming the line.
- **A record keeps the code and the title it was recorded with.** Loading a newer edition changes titles under the same id, so a diagnosis or a procedure (M7) stores the code and its title as they were when it was written, beside the id, as a charge keeps its price and a dispense what the item was. Nothing here keeps old titles.
- **Every load is recorded** in `code_loads` (migration 0032, #316): the set, the SHA-256 of the file's bytes, the counts, when, and the database login that ran it (`session_user`). It is written by `loadCodes` in the load's own transaction, so a load that fails, and a dry run, leave no row. Shared like `codes`, with no tenant, and with no grant to the app role. `load-cli.test.ts` runs the command as a process: its arguments, its exit codes, `--dry-run`, and the message for each kind of failure.
- **Checked on a glibc Postgres** (#316): CI and development use `postgres:17-alpine` (musl), a managed database is glibc. The whole API suite was run once against `postgres:17` (Debian, glibc, `en_US.utf8`) on 2026-10-14. The codes search, with its Devanagari and Tamil words, and every other text search passed as on Alpine. The one failure was the notifier test that builds the app twice: it ran past its 5-second timeout, the same as against the usual database on this machine.
- **The search is `POST /codes/search`** with the term in the body (Searches in the root `CLAUDE.md`), and its answer is `Cache-Control: private, no-store`, as every answer is by the core default (Rules): the favourite marks and the order are one hospital's. Each word starts the code, with or without its dot, or starts a word of the title, in any script: what a word is, and what lower case is, are the database's to say. Only ASCII punctuation is escaped in the expression, because a backslash before a letter is an escape of its own. It is not audited.
- **Favourites first, then the other codes, each in the order of the codes,** read as two reads along the index of the codes in order, not as one sort of the whole set: a page costs the same wherever it is. The cursor says which of the two it is in. A favourite marked or unmarked by someone else between two pages can leave a code out of the later page or show it twice; the web app reads from the first page again after its own change. The order is byte order (`COLLATE "C"`), which is the order the sets are published in and the same on every database.
- **A text index is used here,** which it never is on a tenant table (Sessions, tenants and row-level security): `codes` has no policy, so the trigram index on the title and the prefix index on the code are both read.
- **Marking and unmarking a favourite twice changes nothing,** is audited (`favourite`, `unfavourite` on `code`) and emits `master.changed`. It needs `code:read` as well as `code:manage`, because the answer is the code.
